## 0. 一句话结论

竹子**没有**另写一套生成器：它被实现成一组"生成前展开"的特有参数，
在 `buildTree()` 入口把 `params.bamboo` 翻译成通用的 `trunk / branches / leaves / bark`，
因此风场、蒙皮、节点表、LOD、选择、导出、自检全部原样复用；
竹节是**两层**：实体几何的整圈鼓包（半径调制，`nodeBulge` 可调）+ 贴图上的暗色刻痕环，
两层共用同一个相位零点（`pow(t,nodeCurve) × count = 整数`，见 §3.6），所以既不随竿长漂移、也不偏半节；
竹笋与鸟巢 / 槲寄生 / 彩带是**独立网格 + 独立纯色材质**（`attachments.js`，见 §6），不并进树皮几何；
挂件既支持"数量随机散布"，也支持**逐件手工摆放**（视口点选宿主枝 → `attachments.items[]`，可再编辑/删除，见 §6.4）；
其中鸟巢 / 槲寄生 / 彩带**对所有树种通用**，竹笋仍只在竹种下生成（见 §6.5）。

## 1. 为什么不能只写一个"物种 patch"

| 通用模型的假设 | 竹子的实际形态 | 直接照抄会怎样 |
| --- | --- | --- |
| 一根主干 + 逐层递减的分枝 | 一丛近乎平行的细竿（每竿都是"主茎"） | 竿数只能写死，面板改不了 |
| `applyStage` 把 `lengthRatio` 夹到 `[0.04, 1.2]` | 竿长 = 竹高 ÷ 丛基高，通常 > 1.2 | 竹高设 9 m 只能长出 1~2 m |
| 主干不长叶（`spawnLeaves` 只在 `buildBranch` 里调用） | 每根竿上都有叶 | 若把第一根竿当主干 → 得到一根秃竿 |
| 树皮是"粗糙/白桦/松鳞" | 革质光滑 + 等距竹节环 | 竿看起来像橡木棍 |

所以做法是：**参数组 + build 时展开**。

- 参数组：`params.bamboo`（13 个字段，`params.js` 里有完整默认值与单位注释）；
- 展开函数：`src/core/bamboo.js` 的 `applyBambooParams(params)`，非竹种原样返回（零开销）；
- 调用点：`src/core/treeBuilder.js` 的 `buildTree()` 顶部 `const P = applyBambooParams(params)`；
- 产物：一份"等价于用户设定"的通用参数树，后续流程完全不认识"竹子"这个概念。

`buildTree` 的返回值里多了一个 `effectiveParams`（= `P`），
`sceneManager.rebuild()` 用它创建/更新材质 —— 因为竹子的 `bark.uvScaleV` 是"由竹高与节数反推"的，
若材质继续用原始 `params`，改节数后几何与贴图密度会不一致。

## 2. 结构映射（bamboo → 通用树）

| 通用层 | 竹子里的含义 | 关键字段 |
| --- | --- | --- |
| 主干（trunk） | **根盘**：一块低矮的锥形根茎堆，**整个埋在地面以下**；竿从它的斜面上分出 | `height = baseHeight`（默认 0.4 m）、`baseY = -1.15 × baseHeight`、`baseRadius = rootSpread`（默认 0.8 m）、`fork.enabled = false` |
| L1（branches.level[0]） | **竹竿** | `count = culms`、`pitch = tilt`、`lengthRatio = height / baseHeight`、`taper = 0.42`、`gravity = 0`、`upBias = 0` |
| L2（branches.level[1]） | **侧枝**（上段、短、外张，承载大部分竹叶） | `startT = branchStart`（默认 0.42）、`count = twigs`、`lengthRatio = twigLength / height` |
| leaves | 披针形竹叶（竿上段 + 侧枝） | `shape = 'lance'`、`shapeMix = []`、`perBranch = leafPerTwig`、`size/width/droop` 直接来自竹子参数 |
| bark | 革质光滑面 + 竹节环贴图 | `procedural.style = 'bamboo'`、`vertexColorMix = 0.25`、`uvScaleV` 反推 |

### 2.1 两个必须为 0 的系数（踩过的坑）

`childDirection()` 里会先算 `gravity + phototropism + upBias`，再 `rotateTowardUp()`。
竿子原本只外倾 7°，若沿用乔木的 `upBias = 0.15 rad`（≈8.6°），**方向会被拉回竖直**，
于是 8 根竿几乎重合成一根粗绿柱（首版截图就是这个现象）。
因此竹竿层固定 `gravity = 0, upBias = 0`，外倾角完全由 `pitch = tilt` 决定。

### 2.2 竿长与"竹高"的关系

- `culmRatio = 竹高 / 丛基高`，在 build 时计算，不受 `applyStage` 的夹取影响；
- 场景里 HUD 的「树高」= 丛基高 + 竿长 + 少量长度方差/竹叶外扩，
  **通常比滑杆上的「竹高 (m)」高 0.3~0.9 m**（丛基与叶尖），这是刻意保留的自然差异；
- 竿长方差 `lengthVariance = 0.06`：一丛里各竿略有高低（0.06 时 HUD 误差控制在 ~8% 以内）。

### 2.3 生长阶段与季节如何作用
`applyStage`（`species.js`）末尾追加竹子缩放块：

| 参数 | 随阶段变化 |
| --- | --- |
| `bamboo.height` | `× stage.size` |
| `bamboo.culmRadius` | `× stage.radius` |
| `bamboo.culms` | 按年龄递增（树苗 5 → 成熟 8 → 古树 9） |
| `bamboo.nodeCount / twigs / twigLength / leafPerTwig / leafSize` | 随年龄递增 |

`applySeason` 末尾：

```js
p.bamboo.leafPerTwig = round(leafPerTwig × season.leafDensity)
```

原因：竹叶**不走** `leaves.perBranch` 的"叶预算"链路（竹子用 `bamboo.leafPerTwig` 独立控制），
如果不在这里乘季节密度，秋冬的竹子会和夏天一样密。

实测（seed 777，summer）：

| 阶段 | 竹子高度参数 | 实际 HUD 树高 | 竿数 | 叶数 | 全模三角面 | 蒙皮校验 |
| --- | --- | --- | --- | --- | --- | --- |
| 树苗 seedling | 1.15 m | 2.03 m | 6 | 252 | 3,692 | ok |
| 幼树 sapling | 2.66 m | 3.36 m | 7 | 420 | 4,284 | ok |
| 小树 young | 4.88 m | 5.61 m | 8 | 576 | 4,876 | ok |
| 大树 mature | 8.87 m | 9.95 m | 10 | 840 | 6,060 | ok |
| 古树 ancient | 11.71 m | 12.83 m | 12 | 1,008 | 7,244 | ok |

### 2.4 根盘：竿基不抱在一起（离散度）

现实中一丛竹子不是"所有竿从同一个点冒出来"：竿基散落在地下根茎堆的斜面上，
彼此相隔几十厘米，外圈竿比内圈竿更往外趴。实现方式是：

1. 主干从"细短茎"换成**根盘**（低矮锥形根茎堆）：`baseRadius = rootSpread`、`taper` 由 `rootScatter` 决定；
2. 竿基贴在根盘表面的不同高度（`startT 0.08 / endT 0.88 / startJitter = rootStagger / baseHeight`），
   而根盘是锥形 ⇒ **贴附高度不同 ⇒ 水平半径不同**，竿与竿的基部天然分开；
3. 竿径用 `cfg.radiusAbsolute = culmRadius`（见 §2.4.2）保证"外圈竿不会因为父枝更粗而变粗"。

#### 2.4.1 为什么要埋到地面以下

根盘整块用 `trunk.baseY = -1.15 × baseHeight` 下沉到地下（`treeBuilder.js` 的树干骨架起点由
`new THREE.Vector3(0, trunkBaseY, 0)` 决定）。原因是最初把根盘留在地面上时，1.6 m 宽的绿锥体
在透视里被读成"花盆/石头"（见 `.shots/bamboo-rs-lumpy.png`），竿看起来像插在一个盆里。
埋掉之后地面上只剩**每根竿自己的出土点**，脚部被地面平面遮住，离散感自然。

- `rootSpread = 0`（`clumped`）时**不埋**，退回旧行为：细短茎直接立在地面上，所有竿抱成一团；
- 因为竿基整体低了 ~0.3 m，HUD「树高」≈ 竹高 + 1.0 m（比不埋时略低），不要为它加竿长补偿
  （实测补偿会让 HUD 树高多出 1.5 m，已回退）。下沉取 1.15 倍而不是 1.0 倍，是因为 `startJitter` 会把个别竿抬到 t≈1，1.0 倍时那根竿的基部正好卡在地面上（实测露出小半截断口）。

#### 2.4.2 竿径必须用绝对值（通用链路改动）

`spawnChildren` 原先只按 `fr.radius × radiusRatio` 算子枝基部半径。竿基散开后父枝（根盘）
在贴附点的半径能从 0.25 变到 0.9，同一丛里最粗/最细的竿会差 4 倍。
因此 `treeBuilder.js` 新增 `cfg.radiusAbsolute`（米）：

```js
// treeBuilder.js spawnChildren
if (cfg.radiusAbsolute) {
  radius0 = max(0.0008, min(cfg.radiusAbsolute × variance, fr.radius × 0.92) × radiusScale)
}
```

上限 `fr.radius × 0.92` 是保留的：蒙皮按子枝根部直径在父枝环带上开孔，开口不能比父枝周长还大。
竹子侧给 `radiusAbsolute = culmRadius`、`radiusVariance = 0.08`。

实测（seed 777，`rootSpread` 0 / 0.5 / 1.0）：

| rootSpread (m) | 竿基水平半径（10 根） | 竿基半径（米） | 蒙皮 |
| --- | --- | --- | --- |
| 0（旧行为） | 0.06 ~ 0.19 | 0.045 ~ 0.051 | ok |
| 0.8（默认） | 0.30 ~ 1.14 | 0.045 ~ 0.051 | ok |
| 1.0 | 0.37 ~ 1.43 | 0.045 ~ 0.051 | ok |

（`flare` 只给 0.35：`flare = 1.25` 时最外圈半径会翻倍到 2 × rootSpread，已实测并改小。）

#### 2.4.3 三个参数的映射

| 参数 | 映射到 |
| --- | --- |
| `rootSpread` 根盘半径 (m) | `trunk.baseRadius`；0 → 退回 `culmRadius × 1.6` 细短茎 |
| `rootScatter` 竿基离散 0..1 | `taper = clamp(0.52 - 0.22 × s, 0.26, 0.6)`（锥度越大半径差越大）、`squash = 1 - 0.28 × s`（根盘椭圆）、`culmLevel.spread = 0.15 + 0.45 × s`（方位散布） |
| `rootStagger` 竿基错落 (m) | `culmLevel.startJitter = clamp(rootStagger / max(0.08, baseHeight), 0.02, 0.45)`（贴附高度差 ⇒ 半径差） |

## 3. 竹节：实体几何 + 贴图环（两层）

竹节是**真的建模出来的凸起**，贴图环只负责"暗色刻痕"那一层颜色。

### 3.1 实体几何：半径调制

在蒙皮的半径调制器里加一节（`barkSkin.js` `ringModifier()`、`speedtreeBark.js` `ringModifier()`）：

```js
const gp     = Math.pow(clamp01(f.t), curve)        // curve = nodeCurve (默认 1.3)
const phase  = ((gp * count) % 1 + 1) % 1           // 0 = 正好在节心上（与贴图暗环同一个零点）
const dNode  = Math.min(phase, 1 - phase) / count    // 到最近节心的距离（相位空间）
mod *= 1 + bulge * exp(-(dNode / w)²)                // ① 节部整圈鼓包（宽）
mod *= 1 + ridge * exp(-(dNode / (w × 0.55))²)       // ② 节上窄凸脊（硬边）
```

- `bulge = nodeBulge`（默认 0.2 ⇒ 节心半径 +20%），`ridge = 0.6 × bulge`（默认 +12%）；
- `w = 2.5 / segs`（`segs = 8 × nodeCount`）：σ ≈ 2.5 个环，鼓包跨 4~6 圈环，才是一个"鼓"；
  早先写 `1.5 / segs` 只有 2 圈采样，特写下半径只在一条环上跳一下（像一圈细棱），已被本轮放大；
- 凸脊 σ = `w × 0.55`（早先 0.42 太窄，光滑法线直接抹平）；
- 为什么放在 `ringModifier` 而不是新增分支：节是"周长方向一整圈"的凸起，逐环半径调制就能表达，
  而且窗口宽度估计 `averageRingRadius()` 走同一个调制器，侧枝开口不会算错。

### 3.2 两条几何管线都要支持（踩过的坑）

项目有两条树皮管线（参数 `bark.pipeline`）：

| 管线 | 入口 | 说明 |
| --- | --- | --- |
| `speedtree`（**默认**） | `src/core/speedtreeBark.js` `ringModifier()` | 每枝一根独立管 |
| `skin` | `src/core/barkSkin.js` `ringModifier()` | 单张连续蒙皮 + 分叉切孔桥接 |

**只改了 `barkSkin` 时，画面上一点变化都没有** —— 因为默认走的是 `speedtree`。两条都要加。

另一个更隐蔽的坑：`treeBuilder.js` 里组装 `render` 是**白名单结构**（`buildBranch` 里逐字段列出），
`cfg.nodeBands` 不显式搬进去，蒙皮那侧根本读不到。所以 `render.nodeBands` 必须显式写一行（约 L977）。

### 3.3 纵向分辨率（决定能不能看出"节"）

`bamboo.js`：`culmLevel.segments = clamp(round(nodeCount × 8), 24, 160)`（14 节 → 112 段/竿）。

14 段/竿（旧值）时每节只分到 1 个环，鼓包被插值抹平成斜坡，特写下只是"竿子有点歪"。
8 环/节后每个节心附近有 4~6 圈可用来表达鼓包（`w = 2.5 环`）。
注意：`nodeCurve ≠ 1` 时节心不再正好落在某一根骨架环上（环按 t 均分，节心按 `(k/count)^(1/curve)` 分布），
但因为**蒙皮的 v 就是用同一个 t 算出来的**，贴图环与几何节心仍然逐节重合（见 §3.6）。

代价（实测，seed 20240607 / 默认 10 竿 / 14 节）：全模三角面 **11,100 → 31,380**，
构建 **44 ms → 120~200 ms**。取舍是"能看清节"优先；要换速度就把 8 改成 6（节会明显变软）。

参数 `nodeBulge = 0` 时几何完全退回旧行为（实测 bark 位置径向和 17804.3，与加竹节前逐位一致），
只剩贴图环。

### 3.4 贴图环（颜色层）

`src/core/textures.js` 的 `makeBarkTextures({ style: 'bamboo' })`：

- 革质底：`h = 0.66 + (ridges-0.5)×0.08 + (grain-0.5)×0.04`（几乎没有粗糙树皮的深裂纹）；
- 环位置：`ring = |sin(fy·π·BAMBOO_NODE_BANDS)|`，`fy` 是贴图纵坐标（0..1）；
- 环的两层效果：
  - 节托（微凸）：`+= pow(1-ring, 2.5) × 0.07`；
  - 刻痕（深）：`-= pow(1-ring, 7) × 0.8`；
- 额外**压暗**：`ringDark = pow(1-ring, 7) × 0.55`，写颜色时 `× (1 - ringDark)`。

只做高度场不够：实测 10 m 外的竿上，3 px 宽的暗线完全看不见（首版截图无环）。
压暗系数是让"节"在正常观看距离能被认出来的关键。

### 3.5 环密度 = 每竿节数（反推 UV 重复）

`barkSkin.js` 的原约定是 **UV 以米为单位**（`v = 沿枝弧长`，`u = 周长`）；
竹子（`nodeBands.span > 0`）时 v 改用 `pow(t,curve)*span`（见 §3.6），下面这套反推只决定"repeat 多少次"。
所以"每米重复 R 次"满足：

```
竿高 H × R × BAMBOO_NODE_BANDS = nodeCount
→ R = nodeCount / (BAMBOO_NODE_BANDS × H)
```

- `BAMBOO_NODE_BANDS = 5`（`bamboo.js` 导出，`textures.js` 与本文件共用）;
- 成熟株：`nodeCount 14 / (5 × 9 m) ≈ 0.31` → 每 0.64 m 一道环；
- 早先写成 `nodeCount / BAMBOO_NODE_BANDS`（漏了竹高）会得到每米 40+ 道环，糊成一片。

材质侧通过 `effectiveParams.bark.uvScaleV` 拿到同一个数值（见 1 节的 `effectiveParams`）。

### 3.6 对齐：几何驱动 v + 相位零点（本轮的两处根因）

用户报"实体突起与贴图黑色环对不上"，拆开是两处独立的偏差，**都出在公式里，不是材质采样问题**：

**根因 ①：v 用弧长，节心用 t，两者差一个竿长比例（越靠上越偏）。**
旧写法 `v = arc × uvScaleV`。`arc` 是竿的实际弧长（受外倾、弯曲、逐段累积影响），
而几何节心按 `f.t ∈ [0,1]` 均分。竿实际长度与设定竹高差几个百分点，误差沿竿累计，
到竿顶能偏出接近半个节距 —— 表现为"下面还凑合、越往上越偏"。

修法（`barkSkin.js` / `speedtreeBark.js` 内层循环）：

```js
const nbSpan  = r.nodeBands && r.nodeBands.span ? r.nodeBands.span : 0
const nbCurve = (r.nodeBands && r.nodeBands.curve) || 1
const vCoord  = nbSpan > 0 ? Math.pow(clamp01(f.t), nbCurve) * nbSpan : arc * uvScaleV
```

`span = bamboo.height`，即 v 不再是"量出来的弧长"，而是**从同一个 t 算出来的**；
`uv = (uMeters, vCoord)` 直接写入（repeat 由材质侧 `uvScaleV` 承担，见 §3.5）。

**根因 ②：相位带了 `-0.5`，几何节心整体偏半个节距。**
贴图的暗环在哪里？`ringDark = pow(1 - |sin(π·fy·BANDS)|, 7)`，
峰值在 `sin = 0`，即 `v_tex × BANDS = 整数`。而 `v_tex = v × uvScaleV = pow(t,curve) × count / BANDS`，
所以**贴图暗环落在 `pow(t,curve) × count = 整数`**。
几何侧旧代码写的是 `frac(gp × count - 0.5)`（想当然地认为环心在"半格"），
于是一根 9 m、14 节的竿上，几何鼓包比暗环整体高 `0.5 × 9/14 ≈ 32 cm` —— 特写下就是"突起在暗环上方"。
本轮把两处 `ringModifier` 都改成 `frac(gp × count)`，零点统一。

对齐的实测（`seed 20240607`，默认 10 竿 / 14 节 / `nodeCurve 1.3`，取一棵最长竿的网格）：

| 项 | 数值 |
| --- | --- |
| 几何节心处 `v_tex × BANDS` | `0.000, 1.000, 2.000 … 13.000`（整数，正是暗环峰值条件） |
| 网格实测半径极大处 → 最近暗环中心 | 14 个节全部 ≤ **5.3 cm**（节距 64 cm 的 **8.2%**，约等于一个采样环的宽度；见下方测量口径） |
| 节距（归一化 t） | 基部 `0.1023`、梢部 `0.0559`，比值 **1.83**（上密下疏） |

> 测量口径：按 `uv.v` 分桶取每环平均半径 → 对 `v` 做线性拟合去掉锥度 → 找局部极大得到鼓包中心，
> 再与 `v_tex × BANDS = k` 反算的暗环位置比较。环采样在竿顶约 10 cm 一个，所以量到的是"一个采样环以内"，
> 而不是严格 0；与修复前的常量偏移（`0.5 × 节距 = 32 cm`）不是一个量级。

### 3.7 上密下疏：`nodeCurve`

真实竹子的节间距**基部最长、往上逐渐变短**。实现只改一处：节心的相位从 `t` 换成 `pow(t,curve)`：

```
节心满足  pow(t, curve) × count = k,  k = 0…count-1
→ t_k = (k / count)^(1/curve)
```

- `curve = 1`：等距（旧行为）；`curve = 1.3`（默认）：基部节距 `0.1023`、梢部 `0.0559`（归一化 t），比值 **1.83**；
- 面板范围 1.0 ~ 1.8（1.8 时比值约 3.3，梢部会挤成密节）；
- 因为几何与贴图共用这个 `g = pow(t,curve)`（§3.6），改 `nodeCurve` 时两层**一起变**，不需要另外同步。

### 5.2 为什么不新写一条材质通路

材质侧早已消费 `params.epiphyte.texture`
（`materials.js L1319-1330`：`epiKey → loadTexture({clamp, repairAlpha}) → u.uEpiphyteMap / uEpiphyteEnabled`，

### 5.3 换贴图不重建几何

`params.js` 的 `serializeGroup()`：

- `geometry` 组把 `epiphyte.texture` 替换成空串（贴图变更不算几何变更）；
- `material` 组额外追加 `[['epiphyte.texture', ...]]`。

因此点缩略图只触发 `applyMaterialUpdate`，HUD 的「构建」耗时不跳、树的形态完全不变
（实测：点击前后 `构建 481.8 ms`、`树叶 11520` 均未变，附生卡片立即换图）。

### 5.4 一个顺手修掉的响应式坑

`LeafPanel.vue` 里 `epiphyte` 分组原本是普通对象引用（`const E = state.params.epiphyte`），
撤销/导入参数会整体替换 `state.params`，面板会写到已被丢弃的旧对象上。
已改成 `computed(() => state.params.epiphyte)`（与 `BambooSection.vue` 的写法一致）。

## 6. 竹笋与附属物（`src/core/attachments.js`）

> 本轮（全树种共用）改动见 §6.5；本节 6.1~6.4 记录的是挂件最初只给竹种时的实现与踩坑。

### 6.1 为什么是独立网格 + 独立材质

树皮材质是"贴图 + 顶点色微调"：把挂件并进 `barkGeometry` 会有三个后果 ——
① 红彩带会被竹节贴图染成暗红斑驳、笋身会带上节环；
② 挂件本该是纯色（巢是枯枝棕、槲寄生是叶绿、彩带是大红），贴图会毁掉颜色；
③ 并进去会破坏蒙皮的拓扑验收（`boundary = 0 / components = 1`）。

所以挂件单独一个 `BufferGeometry` + `MeshStandardMaterial({ vertexColors: true, side: DoubleSide })`
（`sceneManager.ensureMaterials()` 末尾追加 `materials.attachments`，`rebuild` 里 dispose 旧网格再新建
`Attachments` 网格）。代价是多一次 draw call、不吃风场/LOD（挂件小、位置静态、不需要摆动）。

`buildAttachments(skeleton, params, seed)` 最初的第一道判断是 `if (!bamboo.enabled) return 空`（挂件只给竹种）。
本轮已放开：鸟巢 / 槲寄生 / 彩带对所有树种生成，只有竹笋仍由 `bamboo.enabled` 把关（见 §6.5）。

### 6.2 几何内容

| 对象 | 几何构造 | 挂点 |
| --- | --- | --- |
| 竹笋 `addShoot` | 13 圈锥体；每 3 圈"鞘唇"外扩 28% 后**成对**收回并压暗（只加宽一圈会被光滑法线抹平）；顶部 3 片苞叶三角形；颜色基部深稻草 → 顶端橄榄绿 | 每根竿 `frames[0]` 旁 0.18~0.42 m 处、`y = 0` 破土；高度 `shootHeight × 0.7~1.05`，半径 `culmRadius × 1.8~2.6` |
| 鸟巢 `addNest` | 外圈 11 根 + 内圈 7 根 + 碗底 5 根交叉短枝（`addTube` 折线扫管，拐弯处重新投影 `side` 防扭成麻花） | L2+ 枝条分叉附近，向上偏 `radius × 1.2` |

### 6.4 手工摆放：点选宿主 + 增删（本轮新增）

数量滑杆只能"多要几个随机挂件"，没法指定挂在哪根枝、哪一段。手工摆放走一条独立通路：

```js
params.attachments.items = [
  { id, type: 'nest' | 'mistletoe' | 'ribbon', node, t: 0..1, size }
]
```

| 字段 | 含义 | 约束 |
| --- | --- | --- |
| `node` | 骨架 `branches` 的下标（与 `branchEdits` 同一套"同 seed/结构下稳定"约定） | 越界/缺失回落到第一根可挂枝 |
| `t` | 沿宿主枝的归一化位置（0 = 枝基，1 = 枝梢） | 夹到 0..1 |
| `size` | 尺寸倍率（1 = 默认） | 夹到 0.2..4 |
| — | 列表上限 | 32 条（`normalizeAttachments` 截断） |

- **与"数量随机散布"并存**：`buildAttachments` 先跑三段随机（竹笋/巢/槲寄生/彩带），再逐件跑 `items`。
  顺序不能反过来 —— 手工挂件不能消耗随机散布之前的 `rng` 调用，否则"点一下视口"会让整丛随机挂件重新洗牌。
  `selftest` 用"随机几何顶点前缀逐字节相同"锁住了这条约束；
- **逐件几何**：`addManualItem` 用 `sampleFrame(branch,t)` 在帧之间线性插值（位置 + 半径），
  避免按帧取整导致滑杆一格一格跳；巢向上偏 `radius × 1.2`、槲寄生向下 `× 1.4`、彩带向下 `× 1`，
  尺寸分别映射到 0.29 / 0.18 / (0.75 长, 0.072 宽) 的基准；
- `stats.custom` 记录手工件数，其余 `nests / mistletoes / ribbons` 与随机散布合并计数；
- **换阶段 / 季节 / 树种不丢手工挂件**：`presets.js → preserveUserBits` 把 `attachments` 整组深拷贝到新预设
  （挂件属于装饰偏好，与树形无关；非竹种不渲染，切回竹子时原来的摆放还在）。

点选实现（`sceneManager.js`）：

1. `setAttachmentPicking(true)`：注册在 `renderer.domElement` 的 `pointerdown` 左键响应，光标变十字；
2. `_pickAttachmentAt(e)`：`Raycaster.setFromCamera` 得到世界射线，再用 `treeGroup.matrixWorld⁻¹`
   把射线换回骨架所在的局部空间（生长动画会整体缩放，漏这一步会"点到却差一个树高"）；
3. `_nearestBranchRay()`：对每条骨架折线的每个线段求**射线–线段最近点对**，
   取最近且距离 < **0.12 m** 的一条，返回 `{ node, t }`（`t` 由线段两端 `frames[].t` 线性插值）；
   距离相同取更靠近相机的那条，避免点前枝却选中后枝。

> **踩过的坑**：本机 WebGPU 后端下 `Raycaster.intersectObject(barkMesh)` 恒返回 0 命中
> （网格 `visible = true`、`position.count = 14849`、射线也确实穿过竿身）。所以没有继续和网格求交硬碰，
> 改成直接对"树皮几何的源头"——骨架折线——求最近距离：不受材质绕序/后端/几何分组影响，
> 也省掉一次全网格求交。阈值 0.12 m 的依据是竿半径约 5 cm，正常命中距离 < 0.06 m。

界面（`BambooSection.vue → 附属物`）：

- 类型下拉（鸟巢 / 槲寄生 / 彩带）+「＋ 点选摆放」→ 点一下视口里的竿或枝，落一件并选中；

- `Esc` 退出点选模式；每次命中后自动退出（否则想转视角时随手一点就会多一件）。

### 6.5 全树种共用（本轮）

原先挂件只跟竹种走（`if (!bamboo.enabled) return`），这一轮放开成所有树种通用。改动分四处：

1. **生成层**（`attachments.js`）：去掉 `bamboo.enabled` 前置，鸟巢/槲寄生/彩带只依赖骨架分支折线；
   竹笋仍由 `bamboo.enabled` 把关（非竹种 `shoots = 0`）。随机宿主仍优先 `level ≥ 2`，
   小树/幼苗一根 L2+ 都没有时回落到任意 `frames.length > 4` 的枝（含主干与 L1），
   避免出现"树上一件挂件都没有"的假失效；
2. **界面**：附属物从「竹子特有参数」里拆出来，成为二级页签 **🪺 附属物**（所有树种可见），
   竹子页签只留 19 项 + 竹笋；点选/列表/增删逻辑原样搬到 `src/components/AttachmentsPanel.vue`；
3. **拾取阈值自适应**（`sceneManager._nearestBranchRay`）：原先写死 0.12 m 是按竹竿半径 5 cm 定的，
   橡树/榕树主干半径可以到 20~30 cm，点在轮廓边缘会"点不中"。改为 `max(0.12, 线段半径 + 0.05)`，
   并且"超出自身阈值的线段直接跳过"，避免细枝抢先命中却因距离太远被整体判空；
4. **挂点统一走法向偏移**（`attachRef` + `perpDir`）：原先手工件一律"向上偏 radius×1.2"，
   随机散布则用**世界竖直**偏移。竹竿半径 5 cm 时看不出差别，但非竹树种的主干半径能到 20~30 cm，
   沿世界竖直方向偏移只是沿着树干轴线滑动 —— 巢会整颗埋进木头里（实测枯树粗干上点巢，只露出半个弧）。
   现在随机散布与手工件共用 `attachRef(f, type, scale, rng)`：
   - 方向取"垂直于枝条、尽量朝上（巢）/朝下（槲寄生、彩带）"；近竖直的主干/竹竿上该方向退化成水平方位
     （用 `rng` 定方位，保证同 seed 确定性）；
   - 偏移量：巢 `max(0.05, radius + 0.29×scale×0.55)`、槲寄生 `max(radius×1.4, radius + 0.18×scale×0.5)`、
     彩带 `max(0.04, radius + 0.02)`；
   - 随机段改成"先取 scale 再 `attachRef`"（巢 `0.24~0.34`、槲寄生 `0.14~0.22`、彩带 `0.5~1.0`/`0.06~0.085`），
     落点方向变了、顶点数不变（彩带后来换成布料网格，三角面已另计，见 §6.6）；
   - `sampleFrame` 现在同时插值帧的 `dir`（帧间 lerp + normalize），`perpDir` 才有稳定的枝轴可用；
     帧没有 `dir` 时退化为 `prefer` 方向。
   水平枝上法向就是正上/正下方，与旧的竖直偏移等价 —— 所以竹子外观不变，只有粗干/近竖直宿主变正确。

### 6.6 彩带 = 布料（`src/core/cloth.js`，本轮）

原来的彩带是"9 段 × 2 顶点的平面布片，摆动用 `sin(t)` 贴上去"。侧面看就是一张纸：
既没有折叠，也没有扭转，宽度方向永远是一条直线。这一轮换成**真的布料求解**。

**算法来源**：three.js 官方 `webgl_animation_cloth` 示例所用的 mass-spring cloth（Simon Green，MIT），
自己重写了一份，不引入 JSCloth / ammo / cannon：

1. 质点网格 5×16（横向 5 格、纵向 16 格），每格 2 个三角形 → 每块布 **160 三角面**；
2. 每个质点存 `p`（当前位置）与 `prev`（上一步位置），速度由两者之差隐式给出（Verlet 积分），
   阻尼 0.995；重力 −9.81；顶边**整行钉死**在挂点（相当于系在枝上的横杆）;
3. 约束是"保持初始长度"的等式，Gauss-Seidel 松弛 4 轮，两端各退一半；
   一头钉死时另一头吃全部修正量（否则布会短一截）；
4. 结构约束（上下左右）+ 剪切约束（两条对角）。**彩带关掉剪切**（`skipShear`）：
   窄条一旦被两条对角距离锁死，扭转也被锁死（实测整条像硬纸板，只能整体倾斜）；
5. 碰撞：宿主枝当成一根**胶囊**（轴 = 该帧枝轴、半径 = 该帧骨架半径），
   布被风吹向枝干时会被推回树皮外侧；
6. 风场与树木同源：方向取 `uWindDir`、强度取 `uWindStrength`（×20 倍，让布"垂着飘"而不是被吹平），
   风速/阵风/湍流取同一批 uniform；另外沿风向加了空间行波相位（空间频率固定 0.22 1/m，
   与叶片风场 `uSpatialScale` 同一量级，但布料不读这个滑杆）—— 布只有几十厘米长，
   各段吃到不同相位，才会拐出 S 形；
7. 初始条件不是平的：沿长度给一个 0.6~1.15 弧度的扭转、沿法向给正弦鼓包、横截面给一段卷边
   （`width × 0.5 × ((2u)² − 0.33)`）。卷边是纯弯曲、不改变边长，所以约束不会把它拉平；
   没有这一层，法线沿布宽方向恒定，整条布一个颜色，看上去就是塑料片。

**构建时预解算 90 步（1.5 秒）**：页面打开看到的是"已经挂了一阵子"的垂坠形状，不是一块刚摊平的布在往下掉。

**运行时逐帧继续积分**（`sceneManager._tickCloth`）：
- 固定 1/60 步长 + 累积器（`_clothAcc` 上限 0.2 s，单帧最多补 3 步）。直接拿帧间隔积分会让
  振幅随掉帧跳变，一次卡顿甚至能把布甩飞；
- 只写挂件几何里属于彩带的那几个顶点（`base + quad*6`，每格 6 个），同时按四边形两条对角线叉积算法线，
  不调 `computeVertexNormals`、不重建几何、不增加 draw call；
- 风场参数每帧从共享 uniforms 读，所以拖"风力/风向"滑杆时彩带和树梢同时变，不需要重建；
- `playing=false`（暂停/关风）时不推进，彩带定格，与树叶风场的行为一致；
- 挂件网格 `frustumCulled = false`：布会飘出构建时的包围球，逐帧重算包围球不划算。

**校验**（selftest §39 累计 8 条布料/彩带断言，合计 **400 通过**）：
- 每根彩带都有布料句柄（`handles.length === ribbons`）；
- 预解算收敛（质点离挂点不超过 `length×1.3 + 0.3` m）—— 早期版本把约束写成了整体位移，
  位置指数发散到 `1e32`，靠这条断言才暴露；
- 同 seed 两次构建的质点数组逐字节一致（Verlet 里没有 `Math.random`，步数固定）；
- 几何顶点块与布料网格一一对应（`quads.length === cols×rows×6`）；
- 逐条长度生效（布料 `length` = 本条长度，不跟全局）；
- 柔软度映射（1 → 2 轮松弛 + 无剪切约束；0 → 5 轮 + 保留剪切）；
- 逐条颜色写进顶点色块（同一 seed、同一位置，只有 color 不同的两次构建逐分量为青色/红色）。

**实测**（`seed 20240607`，鸟巢/槲寄生重做后）：非竹树种挂件三角面 **3,932**

### 6.7 鸟巢 / 槲寄生重做 · 彩带逐条参数

**鸟巢**（`addNest`）。旧版是"11 根外圈 + 7 根内圈细管 + 5 根碗底线"，中间是空的 ——
远看像一把支棱着的树枝，近看像蜘蛛腿。重做后是一只**编出来的碗**：

1. 实体碗壁：12×7 的环面，半径从巢底 0.5R 抬到巢口 1.0R，每个环逐顶点微抖，
   内壁用更暗的色（0.06 一档）收进去 —— 从上方俯视是一个**暗坑**，不是一个洞；
2. 巢口厚度：外壁口沿 -> 内壁口沿再桥一圈，口沿因此不是纸片；口沿半径/高度**逐方位随机**
   （真巢的口都是歪的，正圆会立刻显得像陶罐）；
3. 巢枝：46 根贴在碗壁的短弧（粗细分档、四种褐），再加两圈横着绕满的"箍"和 6 根探出口外的毛边；
4. 尺寸从"半径 0.24~0.34 m"（直径 60 cm 的陶盆）改成 **0.11~0.16 m**（直径 22~32 cm），
   挂点偏移改成 `半径 + 0.5×巢半径`，巢才贴在树皮外侧而不是埋在木头里。

**槲寄生**（`addMistletoe`）。旧版是"1 个主球 + 4 个偏移压扁球 + 3 颗浆果"，是绿气球。
重做后按真实结构：着生短枝（木色）→ 4~5 根两段式的梢（带弯）→ 每根梢 6 片**对生**的披针形叶
（4 个三角形、沿中肋下折，叶缘不是三角形色块）+ 2~3 颗乳白浆果。
叶色取 0.17~0.21 档的深绿（上一版 0.30 在强光 + tone mapping 下会发黄，看着像纸片）。

**彩带逐条参数**（新增）：

| 位置 | 参数 | 说明 |
| --- | --- | --- |
| `params.attachments` | `ribbonLength` 0.75 m | 随机散布的长度，实际 ±18% 抖动 |
| `params.attachments` | `ribbonSoftness` 0.55 | 随机散布的柔软度 |
| `params.attachments.items[]` | `color / length / softness` | 只对这一条生效；新建时从全局抄一份，之后各调各的 |

柔软度不是"调一个系数"，而是映射到布料的三个真实自由度（`cloth.js`）：
① 剪切约束（软塌时丢掉，布才能沿宽度折起来）；② 高斯-赛德尔松弛轮数 `2 + 3×(1-soft)`
（软塌 2 轮、硬挺 5 轮）；③ 吃风增益 `1 + (soft-0.5)×1.2`（0.4× ~ 1.6×）。
柔软度 0.5 时轮数=4、增益=1，与上一版完全一致。

**实测**：巢 2,012 面 / 团槲寄生 654 面 / 彩带 160 面；
非竹挂件合计 **3,932**、竹子 **4,940**；橡树 HUD **206,668**、枯树 **18,443**、竹子 **36,320**。
面板新增三行（彩带颜色 / 彩带长度 / 彩带柔软度），选中手工彩带后再多三行"（本条）"覆盖项，
`ribbon-peritem2.png` 里那条 1.5 m 的青色彩带就是逐条参数改出来的（其余三条仍是全局红色 0.75 m）。

## 9. 明确未做的（边界）

1. **竹节有实体凸起，但没有竹箨（鞘）**：节处是整圈鼓包 + 窄凸脊（半径调制出的真实网格），
   不是"贴图假凸"; 但没有包裹竿基的箨叶/箨痕几何；
2. **竹叶用程序化披针叶**（`shape: 'lance'`），没有复用叶片卡片库；
   —— 如果之后要竹子专用叶卡片，`bamboo.js` 里给 `leaves.texture` 写卡片 URL 即可，
   几何链路已经支持；
3. **竿顶不开口**：没有"中空竹筒"的端面，杆体仍是闭合管；
4. **不做开花/结果**：竹子开花是几十年一遇的事件，`fruit/flower` 在竹种里强制关闭；
5. **节数会带动几何分段**：`nodeCount` 不只影响贴图密度，还决定 `segments = 8×nodeCount`
   （见 3.3 的代价），三角面数随节数线性增长；
6. **挂件不进 LOD，彩带的风是 CPU 布料**：`attachmentsMesh` 是独立网格，不进 LOD1/2；
   彩带靠 `cloth.js` 逐帧求解（约 3 块 × 105 质点），其余挂件静态。它们都不吃 `aWind` 着色器，
   所以 LOD 面板的「当前面数」不含挂件（HUD「全模三角面」含），两处口径尚未统一；
7. **GLB 导出未单独验证**：`exportGLB(root)` 是遍历场景，理论上挂件会被一起导出，但没有开 GLB 核对过；
8. **竹笋只有外形，没有箨叶分层的真实厚度**：鞘唇是同一张锥体上的台阶 + 压暗，不是一片片独立的箨叶；
9. **竹笋亮度偏高**：在软件 WebGL/WebGPU 的强光 + tone mapping 下，顶点色（基部 0.30）仍偏奶油色，
   已两轮调深；未换材质/改光照，避免影响其它树种；
10. **点选拾取不看遮挡**：用"射线–骨架折线最近距离"而不是网格求交（本机 WebGPU 下 `intersectObject(barkMesh)` 恒 0 命中，见 §6.4），
    所以点在叶片前方时也会吸附到叶片后面的枝条；阈值按线段半径自适应（`max(0.12, r+0.05)`，见 §6.5），点到空处不会落件；
11. **`items[].node` 是分支下标**：改竿数 / 竹高 / 种子等结构参数后下标会漂移，挂件可能落到"同一下标对应的另一根枝"
    （不会整批消失：`node` 失效会回落到第一根可挂枝）；要锁死位置就固定结构参数；
12. **撤销按钮现状**：挂件的增删改都已调用 `pushUndo()`（与其它参数动作一致），但 `AutoPanel.vue` 的「↶ 撤销」
    当前恒为禁用（模板里 `!canUndo.value` 对已解包的 boolean 又取 `.value`，且 `canUndo` 的 computed 读的是非响应式数组），
    本轮未改这条既有 UI 缺陷 —— 也就是说参数栈里记了，但界面上暂时撤不了；
13. **手工挂件同样不进 LOD**：与随机挂件共用同一个 `Attachments` 网格（彩带的手工件也是布料，
    同样每帧参与求解）；
14. **附属物默认对所有树种开启**：换树种后默认就会带 1 巢 + 2 槲寄生 + 3 彩带，这是口径变更
    （原先只有竹子才有）；不想要就把三个数量拖到 0 或关掉总开关，该设置会随预设一起保留（`preserveUserBits`）；
15. **鸟巢方向只保证"贴在外侧"，不保证"坐在枝杈上"、也不做树皮曲面贴合**：巢心沿"垂直于枝条、尽量朝上"偏移
    （随机散布与手工件同一条路径），水平枝上等于正上方（像巢坐在枝上），近竖直的树干/竹竿上等于水平外偏
    （像巢贴在树干侧面）；碗底是平面，弧面树皮上会有缝，必要时靠旋转枝条/换宿主规避。
16. **彩带布料是单层、无厚度**：双面材质 + 顶点法线，没有做"布的厚度"和边缘截面；
    远看没问题，贴脸看边是零厚度的；
17. **布料没有自碰撞**：只会互相穿插、也会穿过别的枝条/叶片。碰撞只做了"宿主枝胶囊"这一根，
    因为彩带本来就挂在那一根枝上；要多枝碰撞得给每条彩带传整条骨架，代价是每帧 O(质点×线段)，暂无必要；
18. **布料没有"褶皱贴图"**：明暗全靠网格法线，布料表面只有一层顶点色（沿长度 0.86→1.0，越靠下越暗），
    没有布面纹理、没有织物质感；要加贴图/AO 得另做；
19. **GLB 导出拿到的是"导出那一帧"的布形**：位置属性就是当前帧，导出是静态快照，不带动画；
20. **彩带只在 `playing=true` 时推进**：暂停（⏸）或关风后彩带定格，与树叶风场同步；`windTimeScale`
    会同时缩放布料步进（放慢风 = 布也放慢）；
21. **鸟巢是"壳 + 巢枝"，没有内衬**：碗壁是单层网格（内壁另贴一层暗面），巢枝是嵌在壁上的细管；
    没有苔藓/绒羽内衬、没有枝条之间的物理穿插，碗口是歪的但整体仍是圆环；
22. **槲寄生叶是 4 个三角形的面片**：无叶柄、无叶脉几何，叶簇密度靠"每梢 6 片"堆；
    远看是一团，贴脸看能看出叶子是片；浆果是 4×6 的低模球；
23. **彩带柔软度是"约束/风增益"的映射，不是真实织物参数**：没有弯曲刚度、没有厚度、
    没有经纬向异性；柔软度 0.5 时与上一版布料完全等价（4 轮松弛 + 剪切约束关闭 + 1× 吃风）；
24. **逐条 color/length/softness 只对 ribbon 生效**：巢与槲寄生仍然只有 `size` 一个倍率；
    旧存档里的手工挂件没有这三个字段，`normalizeAttachments` 会补成全局默认（红 / 0.75 m / 0.55）。

### 10.3 苹果果型（`src/core/fruit.js` + `src/core/fruitMaterial.js`）

- `FRUIT_TYPES` 追加 `'apple'`，果型下拉框（`FruitPanel.vue`）新增 `🍎 苹果 (扁球 + 萼洼)`。
- 母线是**略扁圆球 + 顶部萼洼**：口沿之后母线向**内、向下回退**到 y=0.26，形成一个漏斗状凹坑，底部再补一个小凹陷 —— 这是苹果和"球"最大的区别，纯球体在近景一眼假。

### 10.4 视口补光：果实和树皮共用材质带来的连环坑（本轮核心）

**现象**：苹果在视口里是一团近黑的暗紫红；改果色（`#ff6a4a` → `#ffddcc`）、把果径抬到 0.15、关叶片、关 AO —— **颜色几乎不变**，只能看出果面上有纵向条纹，说明 UV/顶点色链路是通的。

**根因**：果实几何是并进 `barkGeometry` 的（`treeBuilder.js` L1926 一带 `mergeGeometries([barkGeometry, ...extraGeos], false)`），与树皮**共用同一份材质和同一张深色树皮贴图**。苹果树皮 `#6b5a4b → #8d7a64` 的线性亮度只有 ≈0.14~0.2，最终 `albedo = map × 顶点色`：

```
红苹果目标 albedo (0.9, 0.25, 0.15)
map (0.20, 0.15, 0.10) × 顶点色 (#ff8a5c 线性 1.0, 0.29, 0.11)
= (0.20, 0.04, 0.011)  →  渲染出来就是暗紫红/近黑
```

**做法**（改动面最小、不动几何拓扑、不动绘制调用）：AO 烘焙之后，把**果实那一段顶点区间**的顶点色乘一个补光系数。

- `fruit.js`：`export const FRUIT_VIEWPORT_GAIN = { apple: 6.0, berry: 5.0 }` + `fruitViewportGain(type)`。
- `treeBuilder.js`：合并时记下 `fruitVertexRange = { start: 合并前树皮顶点数, count: 果实顶点数 }`（果实永远是 `extraGeos[0]`，断口在它后面，合并不重排顶点）；AO 之后按区间乘系数。合并失败时把该区间置空，避免写进树枝顶点。
- 导出侧抵消：`fruitMaterial.js createFruitExportMaterial()` 把材质 `color` 设成 `1/gain`。否则这段 HDR 顶点色进 GLB 会把苹果压成纯白。
- 为什么不用其它方案：① 给树皮贴图开"纯白 texel"让果实采样 —— 贴图是平铺的，白块会在树干上重复出现；② 顶点色直接 >1 抵消 —— GLB 会爆白，且 AO 会把果实压回去；③ 拆独立果实网格 + 独立材质 —— 要同步改导出拆分（`Bark_Fruit`）和自检 6 条以上断言，风险大，本轮未做。

### 10.5 挂果层级与"看得见"（踩得最深的一段）

1. **果实是按枝条遍历顺序生成、并受 `maxCount` 截断的**。上限给小了（实测 `maxCount: 110`）会出现"前几根枝挂满、其余全空" —— 全树只有左侧一团红。苹果因此给到 260。
2. **卡片叶尺度远大于果**。叶片卡片 0.3 m 时，10 cm 的苹果被叶卡整片吃掉，开叶完全看不到果。最终把苹果叶缩到 0.14、海棠叶 0.2，并靠 `perBranch` 补密度。
3. **挂果层级从"最深梢"改成"光枝"**。苹果只挂 L1/L2（叶片只长在 L3~L5 的梢上，L1/L2 本身无叶），周围的果直接暴露；挂 L3/L4 时果全被叶簇吞掉（两轮实拍对比确认）。
4. 苹果枝叶额外留空末梢（`leaves.endT: 0.85`），让梢头的果露在叶簇外侧。

1. **果实与树皮共用材质**：补光系数是"按经验值抵掉深色贴图的乘法"，不是真正的独立材质。好处是零额外绘制调用、导出拆分逻辑不变；代价是苹果/海棠果的亮度依赖 `FRUIT_VIEWPORT_GAIN` 这个常数，改树皮配色要回来复核。
2. **海棠夏态果实基本看不见**：220 颗果主要落在 L3，被叶簇压住；冬态（叶片 480）整树裸枝时才成串露出来。苹果因为只挂 L1/L2 才做到"开叶就能看到"。
3. **苹果冬态仍挂果**：季节系统只控制叶片/花色，不控制 `fruit.enabled`，所以苹果在冬态是"裸枝挂红果"。是否要按季节清果未定（属于产品口径，等确认）。
4. 果实的 `size`（苹果 0.2 m、海棠 0.1 m）都**大于真实值**（8 cm / 1.2 cm），是卡片叶尺度下的可辨识性补偿，不是植物学尺寸。

`branches.level[].gravity` **正 = 向上、负 = 下垂**（mathUtils.js L216）；

### 11.6 已知限制

1. **叶卡颜色不受树种控制**：`leafMat.cardMode` 默认 true，叶片用内置照片卡片，
   卡片自带原色、不走季节调色板；橡树当前抽到的是一张偏白的叶卡，所以截图里
   橡树是"白叶"。这是叶卡库选卡的问题，不是本轮几何改动造成的；要根治得给
   每个树种绑定固定卡片或按季节重染照片。
2. **榕树走 SCA 冠枝**：尺寸由 `sca.crownWidth` 约束，改主干高只抬高冠底，
   不会像逐层枝那样线性放大，所以 11.14m 仍低于野生古榕的 15~20m。
3. **冠幅是包围盒尺寸**：`stats.spread` 取的是最大水平跨度，种子扰动会让
   同树种不同 seed 的冠幅有 ±15% 波动，上表只对 seed 20240607 有效。
