# FastTree 树皮「骨架优先 / 单蒙皮」技术文档

> 范围：本次对话中完成的树皮生成改造，以及随后针对分叉方向、接缝、主枝空心等问题的修复。
> 相关代码：`src/core/barkSkeleton.js`、`src/core/barkSkin.js`、`src/core/meshTopology.js`、`src/core/treeBuilder.js`。
> 适用版本：`package.json` 中的 1.0.0，Three.js 0.186，Vue 3.5。

---

## 摘要

这次改造把树皮从「每根树枝各建一根管子，再靠重叠/布尔/隐式场拼起来」改成了：

1. **先只生成骨架图**（节点、边、半径、父子关系）；
2. 在骨架节点上生成截面环；
3. 沿骨架边扫掠（band sweep）；
4. 分叉处在父枝环带上**真的切一个窗口**，再用 zipper 把窗口边缘和子枝根部环**显式桥接**；
5. 树干基部和所有枝梢/根梢做端盖；
6. 整棵树皮是**一张连续 2-manifold 蒙皮**；果实是独立闭合壳，最后合并。

整条管线不使用 SDF、CSG、最大连通分量过滤，也不做「每根枝条单独建管后再合并」。任何骨架分支都不允许被丢弃；如果极端输入下窗口规划失败，会通过 `failedWindows` 如实报告，而不是假装成功。

最终验收（在最终 `BufferGeometry` 上实测）：

```text
boundary = 0
nonManifold = 0
nonManifoldVertices = 0
components = 1
missingBranches = 0
failedWindows = 0
```

> 注意：渲染几何为了让树皮贴图不出现拉伸带，每圈额外复制了一个 **UV 接缝顶点**。拓扑校验会先按 `geometry.userData.seamPairs` 焊接再统计，所以上面的 `boundary = 0` 指的是**焊接后的物理几何**；直接对未焊接的索引做原始边统计，会看到 UV 缝的边界边（这是正常的、也是行业常见做法）。

## 1. 改造目标与硬约束

### 1.1 旧方案的问题

旧实现的核心问题是「先有管子，再想办法粘起来」：

- 每根树枝单独生成圆柱/管；
- 分叉处靠两根管子互相穿插，加上 collar/extrude/布尔/隐式场来遮缝；
- 一旦要保证单连通、无边界边，就要依赖 CSG 或按位置焊接；
- 分叉的几何质量不可控，容易出现大片斜鳍、空腔、法线错误。

### 1.2 新方案

```text
生长参数
   │
   ├─ growFrames / 分支/树根/分叉主枝 ───────► 骨架图 (barkSkeleton)
   │                                          branches / nodes / edges
   │                                          + parent / attach
   │
   └─ finalizeBarkSkeleton
          │
          ▼
   buildBarkSkin
      ├─ 0. 蒙皮帧: 在子枝贴合高度局部加密父枝环
      ├─ 1. 贴合信息: band / t / azimuth / surfaceNormal
      ├─ 2. 窗口规划: 周向分段 M + 每窗口列数 K
      ├─ 3. 截面环: 肩部定向 + UV 缝复制顶点
      ├─ 4. 环带扫掠: 逐环带铺三角带，窗口格跳过
      ├─ 5. 环桥接: 窗口 rim ↔ 子枝 ring0 的 zipper
      ├─ 6. 端盖: 树干基部 + 每条枝/根末梢
      └─ 7. 校验: 焊接 seamPairs 后统计拓扑 + 分支覆盖 + 体积
```

### 1.3 硬约束

- **不丢分支**：`addBarkBranch` 只追加，不删除；校验要求 `skinnedBranches === skeletonBranches`。
- **不做最大连通过滤**：连通性由构造保证（窗口 + 桥接 + 端盖把每根枝都接到父枝）。
- **不用 SDF / 隐式场 / CSG**。
- **不做「每根树枝单独建管再合并」**。
- **单张蒙皮**：所有树干/树枝/树根属于同一个 `BufferGeometry`，通过 `aNodeId` 归属到节点。
- **窗口失败必须暴露**：`failedWindows` 进入 `stats`，并强制 `validation.ok = false`。

## 3. 数据结构

### 3.1 骨架：branch / node / edge

`createBarkSkeleton()` 返回：

```js
{
  branches: [], // 分支表
  nodes: [],    // 骨架节点表
  edges: [],    // 骨架边表
}
```

`addBarkBranch(skeleton, spec)` 追加一条分支，返回分支 index。每条分支：

```js
{
  index, id, type,        // 'trunk' | 'branch' | 'root'
  level,                  // trunk/root = 0; branch = 1..5
  slot,                   // 模型节点 slot (aNodeId 用)
  parent,                 // 父分支 index；树干为 null
  frames,                 // [{ pos, dir, radius, t, roll, profileRoll }]
  render,                 // 蒙皮渲染参数（周向分段、截面、颜色、风场、半径调制...）
  origin,
  nodeIds, firstNode, lastNode, edgeIds,
  children: [],           // 子分支 index
  attach: null,           // finalize 后填充
}
```

每个骨架节点：

```js
{
  id, branch, index,
  pos, dir, radius, t, roll, profileRoll,
  parentNode,             // 分支内部链；firstNode 在 finalize 时接到父分支
}
```

每条骨架边：

```js
{ id, branch, index, from, to, radius0, radius1 }
```

`finalizeBarkSkeleton()` 对每条子分支，把它的根节点位置投影到父分支折线上，找到最近的段 `bestSeg` 和段内参数 `bestT`：

```js
branch.attach = {
  parentBranch,
  parentEdge: parent.edgeIds[bestSeg],
  segment: bestSeg,
  t: bestT,
  parentNode: parent.nodeIds[bestSeg],
}
```

并把 `nodes[firstNode].parentNode` 接到父分支节点。**这一步不删除任何分支，也不做连通性过滤。**

### 3.2 蒙皮帧（skinFrames）

骨架帧是「每根分支自己的采样点」。蒙皮不能直接拿它切窗口，因为树干一个环带可能很高（默认 ~0.6 m），而树枝直径可能只有几厘米。于是 `buildSkinFrames(branch, branchList)` 在每条**子分支的贴合高度**附近插入两圈环：

```text
epsT = max(0.0015, 1.15 × childBaseRadius / parentTotalLength)
lo = max(parentHasParent ? 0.002 : 0, tAttach - epsT)
hi = min(0.998, tAttach + epsT)
```

- 只影响蒙皮取样，**不改骨架图**；
- 插入帧用 `sampleSkinFrame` 对位置/方向/半径/roll 线性插值；
- 与已有骨架帧相距 `< 1e-4` 的 cut 会被去重；
- 效果：分叉窗口的**轴向高度 ≈ 2.3×子枝半径**，桥接环紧贴树枝基部，不再被父枝环带高度拉成长条斜鳍。

### 3.3 贴合信息（attachOf）

`buildBarkSkin` 为每条子分支建立：

```js
attachOf.set(child.index, {
  parentBranch,
  band,             // 在 skinFrames 中的环带序号
  tGlobal,          // 0..1，沿父枝总长
  azimuth,          // 0..2π，在父枝环坐标系中的方位
  surfaceNormal,    // 父枝表面在该方位的法线（用于子枝肩部）
  childRadius,      // 子枝 ring0 有效半径（含截面/领口）
})
```

**方位角的取值规则**（重要）：

- **树枝**：用子枝 `frames[0].dir` 去掉父枝轴向分量后的**径向方向**求 `azimuth`。
  细枝半径只有几毫米，起点离父枝轴太近；若用起点位置求方位，父枝弯曲会让方位严重失真（实测可差 >90°，窗口就切到父枝另一侧去了）。
- **树根**：用起点位置投影。树根是按世界水平方向放在 flare 表面上的，与倾斜主干的径向分量可能不一致。

`surfaceNormal = side·cos(az) + up·sin(az)`，是父枝环坐标系中的径向单位向量。

### 3.4 窗口计划（plan）

`planBranchWindows` 对每条父分支返回：

```js
{
  M,        // 该父枝周向分段数
  windows: [
    { child, band, start, K, parentBranch }
  ],
  K: Map<child, number>,
}
```

- `start` 是窗口起始**列**，窗口覆盖列 `[start, start+K)`；
- 环列数 `M`，环顶点数 `M+1`（第 `M` 个是 UV 缝复制顶点，见 3.6）；
- 窗口列永远不会切到接缝两侧的列（`start >= 1` 且 `start+K <= M-1`）。

> 未来可扩展：计划完成后把 UV 缝旋转到空闲列（当前缝固定在列 0），可进一步减小靠近缝的子枝窗口偏移。

### 3.5 环与顶点索引

```js
rings[branchIndex][ringIndex] = ring 的第一个顶点在 GeoAcc 中的索引
ringM[branchIndex] = M
```

每个环有 `M+1` 个顶点：

```text
slot 0 .. M-1 : 正常列，物理角度 = slot/M × 2π
slot M        : 第 0 列的复制顶点（位置/法线完全相同，uv.x = uRepeat）
```

环带扫掠、窗口、桥接、端盖都基于这个索引规则。**注意：窗口列号仍然只在 0..M-1 中，且只切 1..M-2。**

### 3.6 几何属性

`GeoAcc` 为每个顶点写入：

| 属性 | 含义 |
| --- | --- |
| `position` | 世界坐标 |
| `normal` | 环法线（含 squash / 肩部方向） |
| `uv` | `u = (列/M) × uRepeat`，`v = 弧长 × uvScaleV` |
| `color` | 顶点色（基色/梢色/色差） |
| `aWind` / `aPhase` | 风场权重/相位 |
| `aOrigin` | 生长动画基点 |
| `aGrow` | 生长区间 |
| `aNodeId` | 生成时的 slot；`finalizeNodes` 之后映射为最终节点 id |

`geometry.userData.seamPairs`：

```js
[[dupVertexIndex, originalVertexIndex], ...]
```

由每一圈的 `[ringStart + M, ringStart]` 组成；只用于拓扑校验/导出检查焊接，不参与渲染。

### 3.7 统计与校验字段

`stats.skin`（`treeBuilder` 暴露为 `stats.skin`，同时返回 `skinStats`）：

```js
{
  skeletonBranches, skeletonNodes, skeletonEdges,
  bridgeStrips, bridgeTriangles,
  caps,
  expectedWindows, plannedWindows, failedWindows,
  radialByBranch,          // 每条分支实际使用的 M
  triangles, vertices,
  validation,              // 见下
}
```

`validation`（`validateSkin`）：

```js
{
  boundary, nonManifold, nonManifoldVertices,
  components,
  triangles, vertices, edges, degenerate,
  skeletonBranches, skinnedBranches, missingBranches,
  volume,
  ok,
}
```

`validation.ok = boundary===0 && nonManifold===0 && nonManifoldVertices===0
                 && components===1 && missingBranches.length===0`

`buildBarkSkin` 在 `failedWindows > 0` 时额外把 `validation.ok` 置为 `false`，并 `console.warn`。

## 4. 算法细节

### 4.1 骨架生成与贴合

- 生长阶段只调用 `addBarkBranch`，把 `frames`、`parent`、`slot`、`render` 写入骨架；
- `finalizeBarkSkeleton` 用点到线段投影找最近段：
  ```js
  t = clamp(dot(p - a, b - a) / |b - a|², 0, 1)
  ```
- 子分支不删除、不重排；父子关系只追加。

### 4.2 蒙皮帧局部加密

见 3.2。目的：

- 把「按父枝整条环带切窗口」改成「按子枝直径切窗口」；
- 让窗口高度与子枝基部尺寸匹配，桥接不至于变成大片平三角；
- 不改变骨架，因此不影响树枝方向/长度/叶片/果实锚点。

### 4.3 周向分辨率 M

`baseRadialSegments(branch, barkDetail)`：

```js
user = round(render.radialSegments × barkDetail)
base = clamp(user, 3, 48)
```

`planBranchWindows` 的初始 `userM`：

```js
isTrunk = branch.parent == null
userM = max(base, (!isTrunk && children.length > 0) ? 8 : 3)
userBoost = round(userM / 3)
```

- 非树干、且有子枝的父枝至少 8 列：窗口按列量化，4 列时偏 1 列就是 90°；
- `userBoost` 是给用户参数的额外余量。自适应分辨率（`requiredM`）可能把 `userM` 完全吃掉；加一个与 `userM` 成比例的余量，保证用户改 `trunk.radialSegments` 等参数时几何仍然变化（参数审计要求）。

最终：

```js
radialCap = max(64, min(4096, 2×childrenCount + 4))
M = min(radialCap, max(requiredM(groups), mFloor) + userBoost)
```

`requiredM` 的迭代（每个环带一组）：

```text
m = userM
repeat up to 10 次:
  total = Σ over children: ceil(m × frac_i) + 2
  if total <= m: break
  m = min(radialCap, max(m + 1, total))
```

- `frac_i = 2·asin(clamp(childBaseRadius / parentAverageRadius, 0.06, 0.92)) / 2π`；
- `+2` 是窗口两侧各留一格缝隙（`rangeFree` 检查 `s-1 .. s+K`）；
- 多个子枝挤在同一条环带时，`requiredM` 会增大 `M`，避免窗口互相挤到很远。

每窗口列数 `K`：

```text
raw_i = max(1, ceil(M × frac_i))
budget = max(childCount, M - childCount)
if Σ raw_i <= budget:
  K_i = raw_i
else:
  // 子枝太粗/太密：按角宽比例缩窗口，保证总占用（窗口+间隔）不超一圈
  K_i = max(1, floor(frac_i / Σfrac × budget))
```

### 4.4 窗口放置

`placeWindows(groups, info, K, M, requireGap = true)`：

- 从离目标方位最近的列开始向两侧扫描；
- `rangeFree` 要求 `s >= 1` 且 `s + K <= M - 1`（接缝两侧各留 1 列）；
- 同一环带窗口之间至少 1 格“桥墩”；
- **相邻环带**的窗口列也必须错开（共享同一圈环棱时，同列窗口会让棱出现第 3 个面）。

失败处理顺序（代价从低到高）：

1. **收窄该子枝窗口**（`kCap` 减半，仍在正确的贴合环带）；
2. 提高周向分辨率 `mFloor += 4`（到 `radialCap` 为止）；
3. 只有 `K = 1` 还放不下时，才把子枝挪到**相邻环带**（先近后远）；
4. 最终兜底：所有窗口压到 `K = 1`，先带间隔，再允许无间隔（列不重叠）；
5. 仍失败：返回已放下的窗口，`failedWindows > 0`，校验失败。

**绝不能为了塞下窗口把分叉挪到离贴合高度很远的环带**——那会把桥接拉成大片斜鳍，看起来像树枝被拉偏。

### 4.5 截面环与肩部

对每条分支、每个蒙皮帧 `i`：

```js
side = basis.side; up = basis.up
if (attach && i <= 1) {
  w = i === 0 ? 0.7 : 1.0
  n = normalize(lerp(attach.surfaceNormal, f.dir, w))
  if (|n|² < 0.04) n = f.dir
  side = normalize(basis.side - n·(basis.side·n))
  if (|side|² < 1e-10) side = anyPerp(n)
  up = normalize(cross(n, side))
}
```

- `i=0`：70% 回到自身方向、30% 贴父枝表面，**根部截面保持圆**；
- `i=1`：完全回到自身方向；
- 早期版本用 `0 / 0.5` 时，ring0 几乎完全贴父枝表面，圆截面被压成椭圆（短/长轴 ≈0.75），近看就是“根部瘪掉”。
- 现在默认 `0.7 / 1.0`：粗枝 ring0 短/长轴 ≥0.91，同时仍保留一点表面贴合，桥接不会太生硬。

这样无论树枝与父枝夹角很小（近切向）还是很大（近法向），都会先贴平父枝再抬出，而不是一圈斜截面直接怼出尖角。

环顶点：

```js
mod = ringModifier(branch, i, angle) × (1 + noise(...))
rr = max(0.0008, f.radius × mod)
p = f.pos + side·cos(angle)·rr·squashX + up·sin(angle)·rr·squashZ
n = normalize(side·cos(angle)·squashX + up·sin(angle)·squashZ)
```

UV：

```js
u = (j / M) × uRepeat        // j = 0..M，j=M 是复制顶点，u = uRepeat
v = arc × uvScaleV
```

`j=M` 的顶点位置/法线与 `j=0` 完全相同；两者通过 `seamPairs` 记录，渲染上形成一条零宽 UV 缝。

### 4.6 环带扫掠与窗口切除

对每个环带 `[ring a0, ring b0]`：

```js
for j = 0 .. M-1:
  j2 = j + 1          // 最后一格用接缝复制顶点，不回到 0
  if 该格属于某个窗口: continue
  tri(a0+j, a0+j2, b0+j2)
  tri(a0+j, b0+j2, b0+j)
```

窗口覆盖列 `[start, start+K)`；因为窗口永远不会包含 0 或 M-1 附近的格子，接缝列不参与窗口切除，缝的拓扑保持完整。

### 4.7 分叉环桥接（zipper）

窗口 rim 的构造顺序（由被删三角面的边界方向推出）：

```text
B_s → A_s → A_{s+1} → ... → A_{s+K}
    → B_{s+K} → B_{s+K-1} → ... → B_{s+1}
```

其中 `A` 是下环（ringA），`B` 是上环（ringB）。子枝根部环按自身自然顺序，但为了减少绕圈，会用 `bestRotation` 旋转到离 `rim[0]` 最近的起点。

`stitchLoops` 按**归一化弧长**在两条闭合折线之间做 zipper：

- 每一步比较 `a 前进` 和 `b 前进` 的下一个归一化参数，选择更小的一侧；
- 生成的三角形分别沿 rim 的旧边方向和子环的反向边方向，保证每条边恰好 2 个面；
- 结果：`bridgeStrips = 非树干分支数`，`bridgeTriangles` 累计。

**中间领口环**：直接 `stitchLoops(rim, childRing)` 会跨越整个洞口，产生狭长的斜三角（斜鳍）。现在在两者之间插一圈 `collar`：

```text
rim --(stitch)--> collar --(stitch)--> childRing
collarCount = max(24, rim.length, childRing.length)
collar[i] = 0.5·sample(rim, u) + 0.5·sample(childRing, u)
```

- 位置/法线/UV/颜色/风场/生长属性都按弧长插值；
- 边界仍是原来的 rim/child 环，所以不产生 T-junction 或新边界；
- 每个窗口多一圈顶点，`bridgeTriangles` 约翻倍（橡树 ~41.6k），换取更均匀的洞口三角面。

如果 `ringA`/`ringB`/`childRing` 缺失，记录到 `bridgeFailed`，`failedWindows` 增加。

### 4.8 端盖

- **树干基部**：只有 `parent == null` 的树干需要封底；中心顶点法线指向 `-dir`；三角扇绕环 0..M-1。
- **枝梢/根梢**：所有分支/树根的最后环都封口；中心顶点法线指向 `dir`；三角扇绕环 0..M-1。

端盖使用环的正常列（0..M-1）；接缝复制顶点不参与端盖，UV 缝在端盖处由 `seamPairs` 焊接后闭合。

### 4.9 拓扑校验

`analyzeTopology` 做四件事：

1. **边计数**：`edgeKey(a,b) = a*V+b`（有序化）；`count==1` → boundary，`count>2` → nonManifold。
2. **连通分量**：并查集；`components`。
3. **顶点流形性**：每个顶点的 link 必须是一个单一有向环；多个环 = 两个面在一点相接（非流形顶点）。
4. **退化面**：三个索引有重复的三角形计数。

焊接选项：

- `weldPairs`：UV 接缝复制顶点 → 原顶点（`geometry.userData.seamPairs`，`validateSkin` 自动使用）；
- `weldPositions`：按精确位置焊接（用于导出的拆分几何；拆节点/UV 缝会复制顶点，但物理上仍闭合）。

`branchSkinCoverage` 用三角形的首顶点 `aNodeId` 检查每条骨架分支的 slot 是否出现过；`validateSkin` 还计算有向体积（法线朝外时为正，仅作启发式检查，不进入 `ok`）。

### 4.10 扭转变形跟随（本次增量）

`growFrames` 给每帧写入：

```text
roll = roll0 + twist × t + profileRoll
profileRoll = 5 点扭曲曲线在 t 处的角度
```

旧实现里子枝只用 `profileRoll` 旋转方向，所以：

- `trunk.twist`（基础标量扭转）只转树干截面，不带动子枝；
- 分叉主枝、树根完全没用 roll；
- 看起来就是“拖了 5 个扭曲点，部分枝干不动”。

修复后，所有“从父枝长出来”的分支都按**完整 `roll`** 旋转自己的生长方向；再生成子树：

- `spawnChildren`：`dir.applyAxisAngle(parentDir, fr.roll)`；`startPos` 的径向方向由旋转后的 `dir` 决定，因此贴附点也绕父轴转；
- 分叉主枝：先算倾斜方向，再 `dir.applyAxisAngle(fr.dir, fr.roll)`；
- 树根：把世界水平的根方向 `rootDirH` 绕主干轴旋转 `rootFrame.roll`；
- 子枝的子树在上述旋转后的 `startPos/dir` 上生成，因此深层枝、叶片/花朵/果实挂点都会跟随。

语义边界：扭转是“绕父枝轴的旋转”，**不弯曲骨架轴**；圆形截面的基础 `twist` 主要靠贴附点/子枝方向体现，而不是靠截面自转（截面自转对圆没有可见效果）。

回归断言（`selftest [26]`）：把树干曲线从 0 改成 `[0,120,240,360,480]`，除树干本身外，L1~L5、分叉主枝、树根全部发生位移/方向变化；`still.length === 0`。

### 4.11 节瘤形态参数（本次增量）

节瘤的半径调制是两个高斯函数的乘积：

```text
size   = knotSize × knotStrength × rand(0.5, 1.5)
spread = knotSpread × rand(0.6, 1.4)          // t 方向半宽
aspread= knotAngle  × rand(0.6, 1.4)          // 角向半宽（弧度）
knot(t, angle) = 1 + size × exp(-((t-k.t)/k.spread)² - ((angle-k.angle)/k.aspread)²)
```

旧默认 `aspread` 随机 0.5~1.6 rad（约 29°~92°），加上幅度，容易在树干上形成“一圈箍”。现在默认：

```text
knotStrength = 0.75
knotSpread   = 0.05
knotAngle    = 0.7 rad
```

UI 提供 `节瘤数量 / 大小 / 强度 / 纵向跨度 / 角向跨度`；`knotStrength = 0` 或 `knots = 0` 可完全关闭凸起。

> 注意：`t=0` 附近的大半径来自**根部 flare**（外扩 + 板根），不是节瘤；两者不要混为一谈。

### 4.12 骨架显示（本次增量）

顶栏「🦴 骨架」按钮 / 快捷键 `K`：

- `sceneManager._updateSkeletonOverlay(result.skeleton)` 从骨架 `nodes/edges` 生成 `LineSegments` + `Points`；
- 颜色：树干金黄、树根橙、树枝按层级青蓝；
- 材质 `depthTest:false / depthWrite:false / fog:false`，`renderOrder=1000/1001`，所以能穿透树皮/叶片看到骨架；
- 只做视口叠加，**不进入几何/导出/统计**；`showSkeleton` 是视图状态，不写参数 JSON，避免参数审计误判；
- 每次重建替换旧叠加层并释放几何/材质；LOD 切换不影响主骨架层。

### 4.13 树根窗口错位与上下移动（本次增量）

粗根在基部的窗口很宽（半径可达树干底半径的 0.9），如果两根根方位接近、又都在同一高度，两个洞口会几乎连成一片。

**自动错位** `roots.autoStagger`（默认开）：

- 先按序号奇偶分配基础层 `tier = k % 2`；
- 再按角向宽度做冲突检测：
  ```text
  rootWidth = 2·asin(clamp(rootRadius / trunkBaseRadius, 0, 0.95))
  conflict = angularGap < (widthA + widthB)×0.55 + 0.06
  ```
- 冲突则升一层，最多 4 层；
- `rootT = clamp(rootBaseT + tier×0.075 + heightOffset + jitter, 0.02, 0.35)`。

这样相互重叠的根会被分到不同高度，窗口不再挤在同一处；代价是部分根会略微上移（仍在树干下部）。

**上下偏移** `roots.heightOffset`（默认 0，UI 范围 -0.15~0.15 相对树高）：整组根沿树干上下移动，正=上移、负=下移。它直接参与 `rootT`，因此根表面、窗口、桥接会一起移动，不会出现“根动了洞没动”。

### 4.14 SpeedTree 风格分枝管管线（默认，旧管线保留）

`params.bark.pipeline`：

```text
'skin'      = 旧管线: 单张连续 2-manifold 蒙皮, 显式窗口 + zipper
'speedtree' = 新管线: 每根骨架分支一根闭合管, 基部领口 + 几何重叠
```

SpeedTree 模式（[`speedtreeBark.js`](src/core/speedtreeBark.js)）的实现：

1. 每条骨架分支独立生成管体（截面环 + 侧壁 + 两端端盖）；
2. 子枝/树根在基部沿自身方向向父枝内部多插 2 圈：
   - `embed = 1.25 × childRadius`；
   - 第 0 圈半径 `1.38r`（藏在父枝内部，作封口）；
   - 第 1 圈半径 `1.14r`（领口）；
   - 之后回到骨架原帧；
3. 不在父枝上切窗口，也不做 rim↔child 桥接；
4. 所有分支管合并成一个 `BufferGeometry`，每根管仍是闭合 2-manifold 分量。

验收语义与旧管线不同：

```text
boundary = 0
nonManifold = 0
nonManifoldVertices = 0
components = 骨架分支数
missingBranches = 0
failedWindows = 0
```

**不是**单连通水密体；壳体之间是几何重叠，不是 Boolean 并集。**默认已启用 SpeedTree 管线**；旧 `skin` 管线/导出/测试仍完整保留，可随时切回。

## 5. 本次对话中定位并修复的问题

### 5.1 分叉处大片斜鳍 / 方向被拉偏

**现象**：树枝基部出现大片平三角鳍，视觉上像树枝在基部被拉弯/偏转。

**根因**：

1. 窗口按**父枝整条环带**切（树干默认 ~0.6 m），而树枝直径可能只有 0.1–0.5 m；桥接被拉成长条斜鳍。
2. 窗口放不下时，规划会把子枝挪到别的环带，最多挪了 5 个环带（约 1 m），洞口跑到贴合点下方 1 m。
3. 子枝 `baseFlare` 把基部撑到接近父枝粗度（L1 +45%，主枝 +62%），窗口进一步变大。

**修复**：

- 父枝在子枝贴合高度局部加密截面环（`epsT = 1.15×r / parentLength`），切口高度≈子枝直径；
- 放不下时先收窄窗口（`kCap` 减半），再提高 `M`，只有 `K=1` 仍不行才挪相邻环带；
- 去掉子枝/主枝/树根的默认 `baseFlare`（默认 0；`onePiece` 仅保留 0.06 的极轻领口）。

**效果**：同一根 L1 分叉窗口从“下方 5 个环带、K=23”变为“正确环带、K=6”；最大桥接边长 1.23 m → 0.55 m；橡树预设树皮三角面一度从 143k 降到 45.6k。

### 5.2 树枝/树根基部出现 180° / 90° 反转

**现象**：树枝基部看起来从洞口反向长回去；线框里基部环与洞口平面差约 90°。

**根因**：

- 树干基部有强烈的 flare/knots 外扩；子枝/树根基部仍按**未调制半径**放在父枝内部，窗口却在外表面，桥接从外向内钻。
- 贴附方位与生长方位是两套独立角度：`childDirection` 用“叶序角 + 随机离散”，`outDir` 只用固定叶序角；细枝还会因父枝弯曲放大方位误差。

**修复**：

- 子枝/树根/分叉主枝基部放到父枝 **flare/knots 调制后的真实表面**上；
- 树根放在 `rootT ≈ 0.05–0.2` 的高度（按根半径自适应），避免环带被 `t=0` 截断成“底缘一个点、上缘很高”的窗口；
- 开口方位改由**生长方向的径向分量**决定（树枝），树根用起点位置；
- 子枝第 0 圈在“父枝表面法线 / 自身方向”之间取 70% 自身方向，前两圈做肩部过渡；

**效果**：橡树树枝窗口（688 个，另有树根窗口）的“基部环与洞口平面”夹角 >90° 从 429 个降到 **0 个**（最大 87°）；“洞口→第一节”表观方向最大 17°，无 >90°。

### 5.3 树干/树枝上的拉伸接缝（图 1 / 图 3）

**现象**：树干或树枝上出现一条竖带，带贴图时纹理被压缩/拉丝；早期也被描述为“法线错误的一条线”。

**根因**：环的 UV 是 `u = (列/M) × uRepeat`，最后一格从 `0.97×uRepeat` 直接连回第 0 列的 `0`；这个四边形把整张树皮在一条窄带里压缩了一次。

**修复**：

- 每圈额外复制一个接缝顶点：位置/法线与第 0 列相同，`uv.x = uRepeat`；
- 环带用 `j2 = j+1`，最后一格连到复制顶点，不再回插；
- `geometry.userData.seamPairs` 记录复制对；
- `validateSkin` / `analyzeTopology` 焊接后再做拓扑统计；
- 果实合并时手动保留 `userData`（`mergeGeometries` 不会自动带过去）；
- 拆分导出检查使用 `weldPositions`。

**效果**：渲染上没有“0.97→0”的压缩四边形；UV 只留下一条零宽缝。橡树最终 `seamPairs ≈ 5434`，焊接后 `boundary=0`。

### 5.4 分叉主枝“插进树干”形成空心（图 1）

**现象**：粗主枝基部出现大洞/空腔，能看到内部面。

**根因**：分叉主枝的 `startPos` 是：

```js
fr.pos + dir × fr.radius × 0.45
```

只沿自身方向深入 0.45R，实际仍在主干内部；窗口在主干表面，桥接从表面钻进内部，形成隧道/空腔。

**修复**（[`treeBuilder.js`](src/core/treeBuilder.js)）：

```js
radialDir = normalize(dir - fr.dir × (dir·fr.dir))
lr = max(fr.radius, lb.radius × trunkModifier(forkT, la, lb.radius) × proj) × 0.95
startPos = fr.pos + radialDir × lr
```

即主枝基部落在 forkT 处主干的**真实表面**上（含 forkShrink/squash/flare），而不是沿 dir 埋进去。

**效果**：3 根分叉主枝的“基部环 ↔ 窗口中心”最大间距约 **0.147 m**；不再出现贯穿式空腔。

### 5.5 树干生长方向与父枝开口不一致（图 2 / 图 3）

**根因与修复**：

| 问题 | 修复 |
| --- | --- |
| 开口方位与生长方向独立 | 树枝用生长方向径向分量求 `azimuth`；树根用起点位置（见 3.3） |
| 列数太少，1 列=90° | 非树干有子枝的父枝最少 8 列 |
| 自适应 `M` 吃掉用户参数 | `userBoost = round(userM/3)` 叠加在自适应结果上 |
| 窗口挤在一起时被挪远 | `requiredM` 按 `K+2` 计间隔；放不下先缩 K、再加 M，最后才挪相邻环带 |
| 小/大夹角出现尖角 | 肩部：第 0 圈 70% 自身方向 + 30% 父枝表面法线，前两圈过渡 |

**最终统计**（橡树，fruit/leaves off）：

```text
β（子枝方向 vs 洞口表面法线）: median 54°, p95 75°, max 87°, >90° 0/688
表观基部方向（洞口→第一节）: median 4°, max 17°, >90° 0
分叉主枝基部-窗口最大间距: 0.147 m
树根径向偏差最大: 0.38 m
```

### 5.6 参数有效性回归（`trunk.radialSegments`）

自适应 `M` 曾把用户设置的 `trunk.radialSegments` 完全覆盖，导致参数审计判定“改了没变化”。加入 `userBoost` 后，用户设置始终对最终 `M` 有影响；自检恢复 299/299。

### 5.7 `onePiece` 的定位

- 只控制两件事：
  1. 导出时把树干/树枝/树根合并为单个 `Bark` mesh；
  2. 给子分支/树根基部加极轻的领口（`0.06` 的 `baseFlare`）。
- 关闭时只是导出保留 `Bark_Trunk/Branch/Roots` 节点拆分，**拓扑不变**。

### 5.8 主干“不规则节瘤”像一圈箍（图 1 类现象）

**定位**：这是设计中的 `knots`（节瘤）半径调制，不是蒙皮/窗口 bug：

- 节瘤是 `1 + size × exp(-(t 高斯) - (角度 高斯))` 的局部半径凸起；
- 旧默认角向半宽 `aspread` 为 0.5~1.6 rad，纵向半宽 0.025~0.09，默认幅度 0.35；
- 角向太宽时，凸起会沿树干绕一大圈，在低模线框里看起来像“箍/环”，而不是局部树瘤。

**修复/增强**：

- 默认 `knotStrength=0.75`、`knotSpread=0.05`、`knotAngle=0.7`，整体更收束；
- UI 增加强度/纵向跨度/角向跨度三个滑杆，可进一步收敛或加强；
- `knotStrength=0` 可完全关闭凸起，`knots=0` 可移除节点；
- 参数审计证明三个参数都会改变几何；拓扑仍 `boundary=0 / nonManifold=0 / components=1`。

### 5.9 主干扭曲不带动部分枝干（历史 bug）

**根因**：见 4.10。`trunk.twist` 没有被用于子枝方向/贴附点，分叉主枝/树根也没用 roll；只有 `profileRoll`（扭曲曲线）部分生效，所以“5 个扭曲点全试过，仍有枝干不动”。

**修复**：`spawnChildren` / 分叉主枝 / 树根全部使用完整 `roll`；子树在旋转后的基点上生成。

**验证**：默认树 188 条分支，除树干外 **187 条全部移动**；新增 `[26]` 断言 `still.length===0`。

### 5.10 顶栏骨架显示

- 新增「🦴 骨架」按钮 / K 快捷键；
- 骨架叠加层与树皮完全解耦，只用于检查节点/父子关系；
- 浏览器实测：`button=true, before=false, after=true, skeletonGroup.visible=true, children=2`（线 + 点两层）。

### 5.11 树枝在开口处偏移 / 根部瘪掉（本次修复）

**现象**：线框下树枝根部与洞口不居中，桥接处出现大片斜三角；着色近看树枝基部被压扁。

**根因 1：窗口环带没有真正对中**。`buildSkinFrames` 在子枝 attach t 附近插入 `t±eps` 两圈，但父枝原有的骨架帧可能落在两圈之间，把一个局部加密带**劈成两半**。`findBandAt` 只能选其中一条，attach t 落在该带的一侧（实测 child 8：窗口带中心 y≈2.963，ring0 y≈2.869，轴向偏差 0.071 m），桥接被拉斜。

修复：在构建 `skinFrames` 时，**删除落在分叉局部加密带内部的原始骨架帧**（仅影响蒙皮取样，不改骨架），保证 `[t-eps, t+eps]` 成为一条完整环带，窗口中心与 ring0 轴向对齐。

**根因 2：肩部权重把根部压扁**。旧版 ring0 法线 = 父枝表面法线（切平面），圆截面投影到垂直于枝轴的方向后短/长轴只有 **0.75**；这就是“瘪掉”。

修复：ring0 法线改为 `lerp(父枝表面法线, 自身方向, 0.7)`，ring1 完全回到自身方向；肩部仍保留一点表面贴合，但根部截面接近圆。

**最终指标**（橡树）：

```text
树枝窗口轴向偏差最大值: 普通枝 0.008 m；粗分叉主枝最大 0.077 m（<0.3×半径+1cm）
粗树枝 ring0 短/长轴最小值: 0.913（修复前 0.75）
窗口对中回归: 轴向偏差 < 0.3×半径+1cm
粗树枝 ring0 圆度 > 0.85 的回归断言: 通过
```

另外，bridge 不再直接 stitch 大三角形，而是在 rim 与子枝 ring0 之间插一圈中间领口环（见 4.7），把跨洞口的狭长斜三角细分为两层，视觉上更接近自然的领口过渡。

### 5.12 两个根窗口挤在同一处 / 树根上下移动（本次修复）

**现象**：基部两根粗根的窗口几乎连在一起，像开了一个大洞。

**根因**：根部窗口很宽（粗根半径可达树干底半径的 0.9）。原来的 `rootT` 只由根半径决定，几条根几乎同高；skin 规划把它们放在相邻的薄环带上，rim 最小距离只有 **0.014 m**（橡树根 1/2）。

**修复**：

- 新增 `roots.autoStagger`（默认开）：按方位宽度检测冲突，把相互重叠的根分到不同高度；相邻序号至少错开一层，最多 4 层；
- 新增 `roots.heightOffset`（默认 0）：整组根沿树干上下移动（相对树高，正=上移，负=下移）；参与 `rootT`，所以根表面/窗口/桥接一起移动；
- 新增回归断言：根部窗口 rim 最小间距 > 0.1 m。

**结果**（橡树）：根窗口 rim 最小间距 **0.014 m → 0.318 m**；默认树 **0.111 m → 0.138 m**。关闭 `autoStagger` 可回到原来的同高行为，再用 `heightOffset` 手动调整。

### 5.13 树枝窗口相互错开 / 洞口三角面细化（本次修复）

**现象**：两条粗枝（尤其分叉主枝与相邻 L1）的窗口在主干相近高度，两个洞几乎连在一起；桥接处还有大的斜三角。

**根因**：

- 分叉主枝原来全部从 `forkT` 同一高度长出，窗口落在同一圈/相邻薄带；
- 主枝高度没有避开已有 L1 枝；
- 桥接直接 `stitch(rim, childRing)`，跨洞口的三角形又长又斜。

**修复**：

- 分叉主枝的 `leaderT` 在 `forkT` 附近按 `k` 错开，并扫描候选高度，**避开已有 L1 枝的窗口高度**：
  ```text
  need = (r_leader + r_child) × 1.15 / trunkLength + 0.012
  ```
- 选择使最近窗口间距最大的候选 `t`；这样每个窗口仍随自己的基部走，不是“洞挪了根没挪”；
- bridge 插中间领口环（4.7），把大斜三角细分为两层。

**结果**（橡树）：

```text
粗树枝窗口 rim 最小间距: 0.256 m（修复前 0.033 m 级）
桥接三角面: ~41.6k（明细化前约 20k；总树皮 115k）
拓扑仍 boundary=0 / nonManifold=0 / components=1
```

### 5.14 按 SpeedTree 思路补一套树皮管线

**目标**：保留旧单蒙皮管线，同时提供一条"分枝管 + 领口 + 重叠"的 SpeedTree 风格管线，彻底绕开窗口/环带量化。

**新管线**：

- 每根骨架分支独立闭合管；
- 子枝/树根基部向内插 1.25r，并加 1.38r/1.14r 两圈领口；
- 父枝不切洞；重叠处由领口遮缝；
- 导出/选择/骨架覆盖沿用原 `aNodeId` 与 skeleton。

**结果**（默认树，无叶无果）：

```text
bark triangles: 13,936
components: 183（= 分支数）
boundary=0 / nonManifold=0 / nonManifoldVertices=0
missingBranches=0 / failedWindows=0
```

与旧管线（24,566 tris / components=1）相比：没有窗口偏移/桥接斜鳍，但多分量、非水密。**默认管线已切换为 SpeedTree**；旧管线保留在「树皮管线」下拉中。

### 5.15 单枝编辑（半径 / 移动 / 旋转 / 扭曲）

**入口**：模型节点树选中一根树干/树枝/树根 → 节点详情下方「单枝编辑」。

**标识**：以骨架分支下标 `branchIndex` 为 key，同一 seed/结构下稳定；树干/树根/分叉主枝也写入 `meta.branchIndex`。

**应用时机**：在 `addBarkBranch` **之前**修改该分支的 `frames`：

```text
radiusScale  -> 所有 frame.radius 乘倍率
moveX/Y/Z    -> 所有 frame.pos 平移
rotX/Y/Z     -> 以第一帧为轴心旋转 frame.pos / frame.dir
twist        -> 按 frame.t 给 frame.roll / frame.profileRoll 叠加扭转角
```

因为先改 frames 再建骨架/子枝/叶片，子枝基部、叶片、果实、窗口/领口都会一起跟随；重置只删除该 `branchIndex` 的 override。

参数保存在 `params.branchEdits`，属于几何组，拖动时自动重建；换 seed / 随机树 / 预设会清空，避免下标串到别的枝上。

### 5.16 树枝环绕式叶/花

**入口**：叶片面板 / 花朵面板 →「树枝环绕生长」。

参数：

```text
leaves.branchWrap / branchWrapTurns
flower.branchWrap / branchWrapTurns
```

实现：

- 只对枝条生效，不再支持树干环绕（旧的 trunkWrap/树干高度/环绕点数已移除）；
- 每根枝条使用自己的 `startT/endT` 与 `perBranch`，方位角步长改为
  `branchWrapTurns × 2π / perBranch`，于是沿枝条轴向形成指定圈数的螺旋；
- 叶/花分别开关，花朵使用自己的 `perBranch/clusterCount`，位置仍在枝条表面；
- 叶片/花朵仍按节点树 L1..Ln 分组，不再有 `L0（树干）` 叶簇组。

**结果**：默认树开启后叶簇数量不变、几何分布改变；花朵几何同样改变；L0 叶簇组不存在。

### 5.17 子枝半径不超过父枝的 80%

**问题**：部分 L1/L2 分支的基部半径接近甚至超过父枝，分叉会显得“枝比干还粗”，也让窗口/领口比例失衡。

**修复**：`finalizeBarkSkeleton` 之后、生成蒙皮之前调用 `enforceChildBranchRadii(skeleton, 0.8)`：

- 逐分支处理，父分支一定先于子分支；
- 取父分支在子枝贴合点 `attach.segment + attach.t` 处的半径；
- 若父枝有 `radiusModifier`（如 forkShrink）或 `squashX/Z`，用收细后/短轴半径作为限制，避免父枝实际变细后子枝反而超限；
- 子枝基部超过 `0.8 × parentR` 时，整根子枝的 `frames.radius`、骨架节点半径、边半径按同一比例缩放；
- 只改半径，不改位置/贴合点/生长方向；
- 统计写入 `skin.stats.radiusClamp`（`clamped`、`clampedByLevel`、`maxRatio`）。

这样 L1 收细后，L2/L3 会继续按新的父半径逐级约束。

**结果**：默认橡树 `clamped=6`（L1 4 / L2 2）；把 L1 的 `radiusRatio` 故意调到 1.3 时 `clamped=27`，所有子枝最大半径比 ≤ 0.800。

### 5.18 单枝 3D 可视化变换轴（Blender 风格）

**入口**：选中单枝后，在「单枝编辑」里默认显示 XYZ 轴；可切「移动 / 旋转」和「世界 / 局部」。

**实现**：

- `sceneManager` 使用 Three `TransformControls`，绑定一个放在枝基的空 `Object3D`；
- 拖动箭头/旋转环时暂停 OrbitControls；
- 拖动过程中按约 80ms 节流把变换写回 `params.branchEdits`，几何 watcher 实时重建；
  重建期间不重置正在拖动的轴，鼠标仍可继续跟手；
- 鼠标释放时再做一次最终提交：
  - 移动：`moveX/Y/Z = 代理位置 - 原始枝基`；
  - 旋转：`qEdit = 代理四元数 × baseQuat⁻¹`，再转成世界 XYZ 欧拉角；
- 代理朝向取骨架枝基真实方向；`baseQuat` 由骨架方向反解已有旋转，避免重复叠加；
- 提交后写回 `params.branchEdits`，几何组 watcher 重建并同步刷新选中节点包围盒。

只对当前 `branchIndex` 生效；切换枝/取消选择按面板生命周期隐藏。

### 5.19 叶/花材质光照与落物继承

**树叶**：原有自发光/反光/散光改用视图空间计算：

```glsl
vec3 treeN = normalize(normal);                 // three 已按 gl_FrontFacing 翻转
vec3 treeV = normalize(vViewPosition);
vec3 treeL = normalize((viewMatrix * vec4(uSunDir, 0.0)).xyz);
```

这样正、反两面都参与高光/散光/透光，不再出现“只有背面生效”。高光的 `dot` 再用
`abs()` 包一层，避免法线朝向导致某一面直接没有高光。

**自发光 (emissive) 正反面一致**：

**现象**：把「自发光强度」拉起来后，只有从背面/树下看叶片、花朵才会亮，正面（朝太阳的一面）几乎没变化。

**根因**：`emissive` 是 three 的标准材质属性，它被加到 `outgoingLight` 上、随后整条像素一起做
`ACES tone mapping × exposure`。正面叶片被强日照推到 tone 曲线高位，同一份加法被压缩到几乎不可见；
背面/树下很暗，同样的加法非常显眼 —— 观感上就成了“自发光只在背面生效”。
所以这不是 `side` / `gl_FrontFacing` 的问题（正反两面走同一份着色器），而是**加法发生的位置**问题。

**修法**（`src/core/materials.js`）：

- 在 `<emissivemap_fragment>` 之后把物理自发光项清零：`totalEmissiveRadiance = vec3(0.0);`
  （选中高亮 / 透光 / 反光 / 散光仍在同一位置叠加，不受影响）；
- 新增 `EMISSIVE_COMPOSITE`，注入在 `#include <colorspace_fragment>` **之后**，按显示空间合成：
  - 色相：向自发光颜色混合（`EMISSIVE_HUE_MIX`）—— 被强光照白的正面也能看出颜色变化；
  - 亮度：显示空间加法（`EMISSIVE_ADD`）—— 与底色亮度无关，亮面/暗面获得接近的视觉增量；
- 材质的 `mat.emissive / emissiveIntensity` 照旧写入，所以 **GLB 导出的 emissive 与以前一致**（视口用合成版，外部软件走标准路径）。

**验收**：`dev/emissive-front-check.html` 在真实 App 里分别统计“正面三角形/背面三角形”覆盖像素的
自发光像素差，比值需落在 **0.82 ~ 1.25**。修复前橡树默认场景约 **0.73**，修复后约 **0.96**（半强度 1.00）；正面像素变化量也从 54/通道 提升到 62/通道。
`selftest` 增加 7 项静态断言（合成片段存在、与 `gl_FrontFacing` 无关、注入在 colorspace 之后、物理项清零、花朵同路径、emissive 仍写入材质）。

**花朵**：`flowerLeafParams()` 把 `flower.emissive/emissiveColor/specular/
specularShininess/specularColor/scatter/scatterPower` 映射进花朵材质；
花朵面板增加对应控件，材质球预览也改用 `createFlowerMaterial`。

**落叶/落叶堆**：

- 新增 `fall.inheritLeafMat`、`litter.inheritLeafMat`，默认 `true`；复选框放在
  “启用落叶/落叶堆积”下方，启用前也能看到当前继承状态；
- 旧页面/旧 JSON 通过 `ensureFeatureDefaults()` 在 App 挂载时补齐默认值，避免
  `inheritLeafMat === undefined` 导致复选框未勾选；
- 落叶顶点着色器增加世界法线/位置，碎片着色器叠加叶材质光照；
- 落叶堆由 `MeshBasicMaterial` 换成独立 `ShaderMaterial`，保留“贴图×顶点色×明暗”，
  再叠加继承光照；
- 关闭 checkbox 时所有继承项归零。

**落花/落花堆**：对应 `flowerFall.inheritFlowerMat`、`flowerLitter.inheritFlowerMat`，
继承源改为 `params.flower`，其余实现同上。

**材质球位置**：

- 树叶材质球从「材质」页移到「树叶」页；
- 花朵材质球新增在「花朵」页；
- 「材质」页只保留树皮材质球。

**面板参数引用**：叶/花/落物面板必须用 `computed(() => state.params.xxx)`，不能把
`state.params.leafMat/fall/litter` 缓存成常量。自动生成/换种子/应用预设会整体替换
`state.params`；旧引用会继续改上一棵树的对象，表现为“滑杆在动、树没变”。

### 5.20 导出贴图成套一致性（diff / nor / rough / alpha 同尺寸 + 同朝向）

**要求**：导出的树叶、花朵、果实的四套贴图必须能直接叠在一起用 —— 同分辨率、同朝向
（`flipY` 一致）、同 UV 变换（`offset / repeat / rotation`）。

**实测到的四类不一致**（`dev/export-map-consistency-check.html` 在 GLB 内部图上量）：

| 来源 | 现象 |
| --- | --- |
| 视口自动法线（`albedoNormalTexture`） | 长边只到 256，且 `flipY=false`；大卡片上传后 `nor` 与 `diff` 尺寸/朝向都不同 |
| 用户自带法线贴图 | 分辨率与卡片不一致（例如 512 vs 1024） |
| alpha 资源 | 独立 data URI，不经 `GLTFExporter` 的 `flipY` 翻转 -> 与 `diff` 上下镜像 |
| 生成的法线 / roughness | 没复制 `diff` 的 UV 变换 -> 图案缩放 / 旋转错位 |

**修法**（`textureNaming.js` 的 `ensureExportTextureAlignment()`，只在导出期间生效，结束 `restore()`）：

1. 以该材质的 `map`（diff）为基准：目标尺寸 = diff 尺寸，目标朝向 = `diff.flipY`；
2. 法线：视口自动法线（`userData.autoNormal`）按当前 diff **全尺寸重新生成**
   （强度取 `userData.autoNormalStrength`，由 `applyAutoNormal` 记录）；自带法线尺寸不符则重采样；
3. roughness：缺失时从 diff 生成（原有逻辑），尺寸 / 朝向不符则重采样；
4. `normalMap / roughnessMap / alphaMap` 统一复制 diff 的 `center / offset / repeat / rotation / wrap`；
5. alpha 资源在 `makeAlphaDataUrl` 里按 `texture.flipY` 先自行翻转（果实高度场 alpha 同理），
   使引擎里 `*_alpha` 与 `*_diff` 朝向一致。

**UV 烘焙**（`textureNaming.js` 的 `ensureExportUvBake()`，紧接对齐之后）：把上述 UV 变换
**乘进几何的 uv 属性**，并把材质上所有贴图的 `center/offset/repeat/rotation` 归零。
原因是 `GLTFExporter` 的 `KHR_texture_transform` 有三处硬伤：① 不写 `texture.center`（three
绕贴图中心旋转，glTF 只能绕原点，旋转 180° 时贴图整体偏出一个贴图宽）；② three 的矩阵是
T·S·R，glTF 规范是 T·R·S，`repeatU ≠ repeatV` 时连 GLTFLoader 都对不上；③ 很多 DCC 不支持该
扩展。烘焙后 GLB 里只剩纯 UV，贴图位置/旋转/平铺与视口逐点一致，也不再写扩展。
同材质的贴图必须共享同一变换、走 0 号 UV 通道、且不被其它材质共用，否则该材质整体跳过
（保持原样，不冒险归零）。几何是克隆后临时挂上去的，`restore()` 换回原几何并释放克隆。

顺带修正视口：`albedoNormalTexture` 现在生成时**使用与源贴图相同的 `flipY`**，法线细节不再相对叶脉上下镜像。

**验收**：`dev/export-map-consistency-check.html` → `EXPORT-MAP-OK`，实测四张图尺寸分别是
leaf `128×128`、flower `217×215`、fruit `1024×1024`（每种材质四张全部一致）；并且
`leaf/flower` 的 alpha 蒙版 IoU（对齐 vs 上下翻转）、`leaf` 的 nor/rough 行相关（对齐 vs 翻转）
都是“对齐”更高；`selftest` 增加 8 项断言（含 `flipY` 反号语义与导出顺序）。

## 7. 已知限制与后续改进

1. **UV 缝位置固定在每圈第 0 列**。窗口被限制在 `1..M-2`，所以理想方位靠近 0 列的窗口会被偏移最多约 1 列；树根最大径向偏差 0.38 m 就来自这里。后续可把 UV 缝旋转到一个**空闲列**（在计划完成后选择 `S` 并把窗口列整体平移），进一步减小偏移。
2. **树根窗口的环带高度**受 flare 梯度影响；虽然 `rootT` 已避免 0 截断，但在强 flare 下仍有少量半径不匹配。
3. **自动错位会让部分根上移**（最多约 0.2~0.3 树高）以避开重叠窗口；如果不想根太高，可关闭 `autoStagger` 并用 `heightOffset` 手动调整。
3. **肩部只作用于前两圈**；极小分段的分支可能没有足够的环来完全过渡。
4. **窗口放不下时仍可能挪相邻环带**（最后手段）；这会轻微拉长桥接，但不会挪远。
5. **UV 缝在导出中是真实拆分**：GLB 里会有重复顶点；外部工具如果不按位置/缝对焊接，会看到 UV 缝的边界边。应用内校验使用 `seamPairs`，这是有意设计。
6. **端盖的 UV 扇**仍可能有轻微 UV 收敛；端盖面积小，通常不可见。
7. **自适应 M 会增加三角面**；如果优先性能，可降低非树干最小列数、`userBoost` 或 `barkDetail` / LOD（`buildTree(p, { validate:false })` 仍做 LOD）。
8. **`validation.ok` 不包含体积**；体积只是启发式（负体积可能来自局部自交/方向问题，不一定拓扑失败）。
9. **极端子枝数**（单环带 ~2000+ 根、5000 roots）依赖 500 ms 规划预算与 no-gap 兜底；超限会 `failedWindows>0`，这是如实失败，不是静默丢枝。
10. **显式桥接不是 CSG**：只处理父—子分叉；如果两根枝条在别处几何穿插，不会自动布尔合并。
11. **扭转是“贴附点/方向绕父轴旋转”**，不是对每根枝条骨架做连续剪切变形；枝干内部形状保持，子树整体跟随。极端大的扭转角（>360°）下，子树会大角度绕轴转，可能出现枝条互相穿插，这是骨架本身的空间冲突，不是蒙皮拓扑错误。
12. **骨架显示是视图状态**（`showSkeleton` 不写入参数 JSON / 导出），刷新页面会回到关闭；需要持久化可后续放进 scene 参数并加入审计豁免。
13. **节瘤是半径调制**，不做真实树皮开裂/树瘤几何；`knotStrength` 过大时仍可能形成明显鼓环，建议配合 `knotAngle`/`knotSpread` 调整。

## 8. 调试手册

### 8.1 快速检查

```js
import { buildTree } from './src/core/treeBuilder.js'
import { defaultParams, normalizeParams } from './src/core/params.js'
import { applyPreset } from './src/core/presets.js'

const p = normalizeParams(applyPreset(defaultParams(), 'oak', 'mature', 'summer'))
const r = buildTree(p)
console.log(r.stats.skin.validation)        // boundary / nonManifold / components / missingBranches / volume
console.log(r.stats.skin.failedWindows)     // 必须是 0
console.log(r.barkGeometry.userData.seamPairs.length)
```

### 8.2 查看窗口计划

```js
import { buildBarkSkin } from './src/core/barkSkin.js'
const skin = buildBarkSkin(r.skeleton, { validate: false, debug: true })
const { plan, attachOf, skinFrames } = skin.debug
```

`plan` 是 `Map<parentIndex, { M, windows, K }>`；每个 window 有 `{ child, band, start, K }`。

### 8.3 常见症状 → 检查项

| 症状 | 优先检查 |
| --- | --- |
| 树皮竖条/拉丝 | `seamPairs` 是否存在；是否有人绕过 `validateSkin` 直接统计边界；UV 是否 `j2=j+1` |
| 分叉处大片斜鳍 | 窗口是否被挪到远处（`window.band` vs `attachOf.band`）；窗口高度是否≈子枝直径 |
| 树枝看起来反向/90° | `attachOf.azimuth` 是否用生长方向（树枝）；子枝基部是否在父枝真实表面 |
| 主枝空心/大洞 | 主枝 `startPos` 是否用 `radialDir × surfaceR`，而不是 `dir × 0.45R` |
| `failedWindows > 0` | 该父枝 `radialCap`、`expectedWindows/plannedWindows`、是否超过 500 ms 规划预算 |
| 导出后 split 零件 boundary>0 | 分叉缝天然开放；用 `analyzeTopology(..., { weldPositions:true })` 校验合并树体 |
| 参数改了没变化 | 是否被自适应 `M` 吃掉；`userBoost` 是否存在 |

### 8.4 浏览器

- `dev/skin-check.html`：拓扑、极限配置、GLB 拆分、`onePiece`；
- 临时调试页只用于定位，不应提交；启动 dev server 后通过 CDP/Chrome 截图；
- `npm run check` 的 MCP 自检需要 Chrome 上打开应用页面。

## 10. 一句话总结

**骨架图决定“树枝往哪长、多粗、谁是谁的父枝”；蒙皮只在父枝上按子枝直径切窗口，用显式环桥接把子枝根部缝进同一张 2-manifold 蒙皮；UV 缝通过复制顶点 + 焊接校验做到“渲染无拉伸、几何仍封闭”。** 所有方向/对不齐问题，最终都归到两件事：**基部是否落在父枝真实表面**，以及**开口方位是否跟随真实生长方向**。
